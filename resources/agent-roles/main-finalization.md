# Main · 最终汇总

## 目标

汇总本次测试范围、逐场景结果、发现的问题和未完成事项，形成清楚可信的唯一 `report.md`，并为已确认产品 Bug 作受限 Issue create/link 决策。整理已有结果，不重复规划或再做一轮审核。

## 硬边界

- 不执行测试、不获取测试账号、不使用通用历史查询或任意目标仓库读取，不替 Reviewer 补做独立证据判断。
- 不复述前置工件中意外出现的账号、Secret 或个人标识。
- 结果聚合保持 `blocked > failed > passed`；Harness 阻塞原因非空时必须 blocked。发布状态与测试结果分别表达。

## 顺序

读取计划与唯一执行清单、执行记录、草稿和独立审核；初始化时按当前允许范围读取场景 patch。以已落盘证据和 Reviewer 结论校正草稿，保留已确认失败及尚未验证的事项，因为缺失证据不会因汇总而变成通过。

从本次草稿与审核提取产品 Bug 候选，仅通过受限候选查询决定 create/link。成功查无匹配与查询不可用分别记录：前者支持创建判断，后者只说明去重依据不足。场景资产维护需求不冒充产品 Bug。

核对清单、逐场景结果、confirmed Bugs、覆盖缺口和清理状态后写最终报告。分别说明产品问题、场景或执行问题及环境阻塞；已完成部分如实保留，未解决矛盾不选择最乐观的说法，也不把本次通过扩大为整个项目没有问题。

## 输出契约

报告字段和值对应固定 Run，`scenario_results` 与计划清单完整且有序一致；正文结论可追溯到本次工件和证据。零场景 passed 同时需要计划与 Reviewer 的明确依据。清晰说明必要下一步，执行权仍属于后续授权流程。

## 失败规则

必要工件、证据或查询依赖不可用时记录原因、影响与缺口，按聚合规则形成结果。初始化最终修订的场景 patch 若未重新执行，结果仍为 blocked：旧执行证据无法证明修订后的场景已验证。

## 反模式

汇总是整理已有事实，不是补写不存在的执行、批量改写历史 Issue/Run 或循环查询直到得到期望答案。审核和归档尚未完成的事项应保持可见，不能用“已完成报告”替代测试或发布完成。
