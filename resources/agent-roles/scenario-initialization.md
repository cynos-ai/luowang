# 陌生项目初始化附加规则

## 目标

从固定初始 target 建立少量、有依据、可执行的业务场景基线。以核心用户结果和风险组织候选，而不是穷举页面、按钮或接口。此处只补充初始化交接，场景设计与格式沿用 Main · 规划规则。

## 硬边界

- Preflight 缺少可信仓库、非生产环境、测试账号或必要读取能力时保持 blocked。
- 静态勘察与候选综合使用不同 Main · 规划 Session；运行时侦察与候选验证使用不同 Runner Session。角色只消费当前阶段允许的工件，不假装继承前序对话。
- 能力表只在当前计划或报告中使用，不创建长期能力图或额外资产体系。

## 顺序

### 先建立理解，再形成候选

静态 Main 从角色、入口、核心目标、状态变化、权限/校验/持久化风险和依赖形成临时能力表：“角色/入口 → 结果 → 风险 → 依据/待观察项”。缺少项目理解文档时在计划中保留临时理解，并安排低风险运行时侦察；避免不可逆数据操作。

侦察记录已检查入口、角色状态、观察、未达路径、证据与清理事实。未观察到不等于功能不存在，运行结果也不自动决定正确期望，所以候选 Main 先读 plan、execution、draft-report，再按需核对 target。

候选 Main 更新同一个 `plan.md`，保留静态依据与必要侦察摘要，再按业务语义合并或复用场景，补充候选、依据、状态理由、执行清单与缺口。后续角色只看到工件，这次更新是把新发现传给验证的必要交接，不以对话总结代替。

### 验证候选，判断是否足够

有 patch 时由 Harness 校验、按策略处理审核与应用；无需审核时按更新计划验证。所有新增或内容修改的 approved 场景纳入执行清单，正文完全不变的 rename 不强制重跑。无 patch 时复用固定 target 的 approved 场景，仍按新计划验证；侦察不能替代正式执行。

停止前复查：主要角色与入口是否已检查，每项核心能力是否有成功路径候选或明确缺口，适用风险是否覆盖，approved 是否有依据、策略允许时是否已执行，入口/schema/既有测试是否还揭示遗漏的高价值能力。预算只说明为何停止，覆盖判断来自这些事实。

## 输出契约

候选 Main 成功写入更新计划；需要资产维护时同时交付与计划一致的完整场景 patch。期望不确定保持 draft，环境不可用时只提交 draft 与阻塞说明。没有可信候选时在计划中解释原因，无需伪造 patch。

人工审核路径在候选阶段结束，沿用两工件特殊报告和安全摘要，不等待合并或启动额外验证。其他路径按更新清单进入隔离验证、Reviewer 和最终汇总；空清单也走零场景独立审核。

## 失败规则

首次分支、固定 target、发布或必要验证条件不成立时，初始化完成声明保持受阻。最终修订未经重新执行的 patch 仍为 blocked，因为已取得的证据对应的是先前版本。无 patch、空清单或没有发现错误都不是初始化完成的充分依据。

## 反模式

能力表是当次理解工具，不是长期目录或场景数量指标。候选数量少应来自语义复用与有据取舍，而不是省略核心风险；前序 Session 做过侦察也不代表新候选已经通过。
