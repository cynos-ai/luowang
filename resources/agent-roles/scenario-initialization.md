# 陌生项目初始化附加规则

## 目标

从固定初始 target 尽可能全面地整理项目业务场景，覆盖主要用户流程、常见异常和重要边界，并实际验证形成可维护的基线。数量由项目需要决定，不以少量为目标，也不要求绝对完整或穷举页面、按钮、接口及所有组合。此处只补充初始化交接，场景设计与格式沿用 Main · 规划规则。

## 硬边界

- Preflight 缺少可信仓库、非生产环境、测试账号或必要读取能力时保持 blocked。
- 静态勘察与候选综合使用不同 Main · 规划 Session；运行时侦察与候选验证使用不同 Runner Session。角色只消费当前阶段允许的工件，不假装继承前序对话。
- 能力表只在当前计划或报告中使用，不创建长期能力图或额外资产体系。

## 顺序

### 先建立理解，再形成候选

静态 Main 从需求、使用流程、入口和已有测试理解项目，在计划中简述主要功能、相关角色、重要风险与待观察项，作为临时能力表用于查漏，不逐接口铺设台账。缺少项目理解文档时保留临时理解；对不清楚的入口和执行条件安排低风险侦察，避免不可逆数据操作。

侦察记录已检查入口、角色状态、观察、未达路径、证据与清理事实。未观察到不等于功能不存在，运行结果也不自动决定正确期望，所以候选 Main 先读 plan、execution，再按需核对 target。

候选 Main 更新同一个 `plan.md`，保留静态依据与必要侦察摘要，再按业务语义合并或复用场景，补充候选、依据、状态理由、执行清单与缺口。后续角色只看到工件，这次更新是把新发现传给验证的必要交接，不以对话总结代替。

### 验证候选，判断是否足够

有 patch 时由 Harness 校验、按策略处理审核与应用；无需审核时按更新计划验证。所有新增或内容修改的 approved 场景纳入执行清单，正文完全不变的 rename 不强制重跑。无 patch 时复用固定 target 的 approved 场景，仍按新计划验证；侦察不能替代正式执行。

停止前复查已知主要角色、流程、常见异常和重要边界，结合入口与既有测试补漏；候选有依据，策略允许时按清单执行，未覆盖或未完成项如实保留。完成这次检查即可结束本轮，不为追求绝对完整反复扩展假设；必要缺口仍按共同规则阻塞，不把预算耗尽写成覆盖完整。

## 输出契约

候选 Main 成功写入更新计划，并在同一次 write_plan 调用中按更新后的执行范围显式重定 requiresBrowser（不沿用侦察需求）；需要资产维护时同时交付与计划一致的完整场景 patch。期望不确定保持 draft，环境不可用时只提交 draft 与阻塞说明。没有可信候选时在计划中解释原因，无需伪造 patch。

人工审核路径在候选阶段结束，沿用两工件特殊报告和安全摘要，不等待合并或启动额外验证。其他路径按更新清单进入隔离验证、Reviewer 和最终汇总；空清单也走零场景独立审核。

## 失败规则

首次分支、固定 target、发布或必要验证条件不成立时，初始化完成声明保持受阻。最终修订未经重新执行的 patch 仍为 blocked，因为已取得的证据对应的是先前版本。无 patch、空清单或没有发现错误都不是初始化完成的充分依据。

## 反模式

能力表只辅助当次查漏，不是长期目录。场景数量多不等于覆盖全面，数量少也不等于质量高；检查实际业务是否遗漏或重复。前序 Session 做过侦察不代表新候选已经通过。
