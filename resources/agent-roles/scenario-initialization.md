# 陌生项目初始化附加规则

## 目标

从固定初始 target 建立少量、可追溯、可执行的长期场景基线，而不是穷举项目表面结构。

## 硬边界

- Preflight 缺少可信仓库、非生产环境、测试账号或必要读取能力时必须 blocked。
- 静态勘察和候选综合分别使用新的 Main · 规划 Session；运行时侦察和候选验证分别使用新的 Runner Session。
- 多个 Session 只通过允许的落盘工件交接，不共享完整对话。
- 临时能力图只能存在于本次计划或报告正文，不创建长期能力图文件。

## 顺序

1. 静态勘察主要角色、入口、核心能力、关键状态变化、权限/校验/持久化风险和外部依赖，形成“入口 → 结果 → 风险 → 依据/待观察项”能力表。
2. 规划低风险运行时侦察，避免不可逆数据；记录已检查入口、观察、未达路径、证据和清理事实，未观察到不等于功能不存在。
3. 综合静态与运行证据，把业务结果相近的步骤合并为少量高价值候选场景，检查语义重复、核心缺口和停止条件。
4. 在同一个 `plan.md` 保留静态依据和必要侦察事实，写入候选、依据、状态理由和唯一 `## execution_scenarios`。
5. 有候选 patch 时先校验并应用，再对更新计划中的清单执行成功路径和必要拒绝路径；无 patch 时按更新计划复用固定 target 的已有 approved 场景，空清单也走零场景独立审核。
6. 逐项说明主要角色/入口、核心能力候选或缺口、适用风险覆盖、approved 依据、执行完成情况和最后复查结论；工具或时间预算只能作为停止原因。
7. 不确定的期望保持 draft，记录冲突和覆盖缺口。

## 输出契约

每个 approved 候选必须有可追溯依据；候选资产仍只能写入场景目录 patch。候选 Main 必须成功更新同一个 `plan.md`，不能用对话总结替代交接。最终修订若未重新执行，报告必须 blocked。无 patch 不是无需测试的依据；没有可信候选或期望不明时记录 blocked/draft。

## 失败规则

没有可信候选时不伪造 patch；首次分支、固定 target、场景发布或验证条件不成立时不声称初始化完成。

## 反模式

不得按页面、按钮、路由或 API operation 机械生成场景，不得建立 suite、catalog、journey 或长期能力模型，也不得让一个 Session 假装继承另一个 Session 的对话。
