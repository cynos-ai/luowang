# 罗网（LuoWang）项目理解

> 本文件由 Cynos 项目理解流程维护。它记录跨代码和需求的稳定项目理解，不代替具体需求的 intent、spec 或 plan。

## 项目解决的问题

罗网是一个独立部署的 AI 场景测试 Harness。它面向已经使用 AI 参与需求和开发的软件项目，把分散在需求、代码、运行行为、临时测试和人工判断中的信息，收敛为可持续维护的业务场景、可审核的测试执行和可追溯的正式结果。

项目的主要使用者是负责配置测试环境、触发测试、审核场景资产和处理测试结果的项目负责人或测试操作者。开发和需求系统消费罗网写入 GitHub 的报告与 Issue，但不由罗网直接调度。

项目公开托管在 `cynos-ai/luowang`，采用 GNU Affero General Public License v3.0（AGPL-3.0）。许可证允许商业使用，但要求分发的衍生作品继续使用同一许可证；修改版通过网络提供服务时，也必须向用户提供完整对应源码。

## 关键概念

- **目标仓库**：一个罗网 MVP 部署只管理一个操作者信任的 GitHub 仓库。
- **场景测试分支**：默认名为 `scenario-testing`。产品代码、需求文档、长期场景和正式报告只有进入该分支后，才属于罗网的正式测试事实。
- **场景资产**：描述业务结果的长期 Markdown 文件。状态仅有 `draft`、`approved`、`deprecated`；标签用于检索和加权，不构成测试套件。
- **Run**：针对一个不可变 `target_commit` 的测试运行，记录 `base_commit`、实际纳入分析的提交、触发来源、场景结果和证据。
- **角色隔离**：Main 负责理解变化、维护/选择场景和形成计划；Runner 执行；Reviewer 在独立上下文中审核；新的 Main 汇总最终报告。
- **推进**：只更新罗网数据库中“上一次已完成测试目标”，用于确定下一批范围，不代表对整个 Git 分支覆盖率的推断。
- **归档与索引**：测试主流程先产生本地工件；独立归档任务负责 Git、SQLite、PR 和 Issue 副作用；索引任务再从 Git 重建网站读模型。
- **项目开发分支**：`main` 保存正式发布历史，`develop` 集成下一版本，短期 `feat/*` 和 `fix/*` 通过 PR 合入；目标仓库中的 `scenario-testing` 只保存被测项目的测试事实，不参与罗网项目的开发和发布。

## 主要系统边界

罗网的长期进程统一承载网站、HTTP API、认证、配置、触发器、顺序队列、Agent 调度、归档和仓库索引。它连接以下外部系统：

- GitHub 仓库、Pull Request 和 Issue；
- 模型 Provider 与 Pi Agent Runtime；
- 目标项目的测试或预发布环境；
- Playwright 浏览器能力；
- S3-compatible 对象存储。

场景和正式 Markdown 报告以目标仓库 Git 为事实源。SQLite 保存控制台配置、加密 Secret、详细 Run 记录和可重建的网站缓存。本地运行目录保存尚未完成归档的工件。截图、trace 等大文件存入对象存储，Git 报告只记录稳定地址。

## 有意设计的决定

- 罗网与写需求、写代码和修复 Bug 的 Agent 解耦；它只报告问题，不修改产品代码或调度修复。
- MVP 固定为单租户、单仓库、单测试分支、单测试环境、单实例顺序执行，避免提前引入平台化和并发复杂度。
- 测试选择由 AI 综合需求、累计 diff、历史 Run/Issue 和场景语义完成，不维护手工 suite。
- Runner 的结论必须经过独立 Reviewer 审核；角色通过落盘工件交接，不共享完整对话。
- 运行期间不持续把每次工具调用结构化写入数据库；完成后再批量、幂等归档。
- `blocked`、`interrupted`、证据缺失、清理失败和归档失败不能伪装为通过，也不能错误推进测试目标。
- 场景变更需要人工确认时通过短生命周期 Run 产生 PR，不让 Agent 进程跨小时等待审批。
- Main 只产生场景目录内的 patch；Archiver 只原样发布已验证场景 patch，并只为当前 Run 新增正式报告，不能改写产品、需求或历史报告。
- 管理员初始密码只从 `LUOWANG_ADMIN_PASSWORD` 建立 Argon2id 哈希，不提供匿名初始化或默认密码，已有哈希不被环境变量覆盖。
- 不引入完整 Gitflow 的 release/hotfix 分支；正式版本紧急修复仍使用 `fix/*`，合入 `main` 后同步回 `develop`。
- MVP 验收使用独立样例仓库和独立本地或非生产样例应用，不把罗网项目仓库纳入目标仓库配置，也不建立实例互测架构。

## 重要约束和风险

- 罗网具有读取仓库、执行命令、访问测试环境和保存凭据的高权限；Secret 必须最小暴露并与被测命令环境隔离。
- MVP 单容器不是恶意代码沙箱，只允许执行操作者信任且已进入场景测试分支的代码，禁止连接生产环境。
- 场景测试分支应禁止 force-push 和 rebase；历史断裂时必须停止自动测试并由操作者重新指定起点。
- Git、Issue、PR、对象存储和数据库归档都必须支持幂等重试，避免重复发布或错误推进。
- 正式结论依赖测试环境、凭据、浏览器/模型能力和证据可用性；缺少必要条件时应明确 blocked。

## 当前基线

当前 MVP 的已确认产品、架构、安全和验收边界记录在 `docs/changes/luowang-harness-mvp/spec.md`，分阶段实现顺序和每阶段证明记录在同目录 `plan.md`。当前已完成 Phase 0–6：包括 GitHub Repository Service、场景分支控制、Markdown 索引、Agent Run、headless 浏览器与 OSS 证据、幂等归档，以及 Git/Cron/API/人工请求共用的 SQLite FIFO 队列、自动合批、定时任务和 interrupted 恢复。目标测试项目固定为 `cynos-ai/cynos-website`，其凭证只保存在 LuoWang 本地被忽略的 `.env` 或网站 Secret Store，不进入项目理解文档和 Git。
