## 4 Phase 1 请求停止和持久化基础

### 实施顺序

1. 审计现有 queue、recovery、run store、SDK 和 Docker owner，列出最小字段变更：停止请求/原因/时间、来源请求关系以及读模型需要的数据。采用旧记录 null/unknown 的兼容迁移。
2. 用现有固定版本 SDK 验证真实 prompt 中止、工具中止和 MCP shutdown，不升级依赖以回避问题。先证明资源能结束，再实现页面按钮。
3. 实现 queued 原子取消；取消与认领、重复点击竞争只有一个持久化结果。
4. 将停止检查放到已认领准备、Session 创建、每个后续阶段和工具开始边界。停止信号下传到实际操作；Git 写入不确定时保留与核对原事实。
5. 按 Spec 实现 30 秒合作退出期限及所属资源的有界终止，完成 Harness 收尾和资源核对；无法确认执行退出时保留占用与告警。
6. 处理重启、完成与停止竞争、准备请求恢复；补全 UI/API 的 scope、认证、同源与幂等契约。

### 必需验证

覆盖 queued、尚无 Run 的准备、四个正常角色阶段、初始化分流、收尾、待归档、完成后的停止；既有完成报告不得改判。A 停止/B 正常、重复停止、同项目排队、SDK abort 后返回迟到结果、不可退出资源、Git 已 push 但响应未知均有案例。

工程模拟用于确定竞态；生产 SDK/真实 MCP/实际 Docker 证明中止和所属资源退出。单测返回 Promise 不能替代实际关闭证明。停止后的重启不得 requeue，同一请求保持唯一 Run。

退出：AC-RR-04–08；schema 和回退说明进入本 Plan 实际记录。阶段未通过时不提前展示“已安全停止”。

## 8 Phase 5 模型专项和既有质量欠账

### 六类专项

实施前冻结基线和六类判据，候选完成后按 Spec 执行 72 个案例运行：六类各两个正反子例，每个子例在两版本各重复三次。每例保存版本/角色哈希/模型、完整实际输出、证据读取、必要步骤、结果、用量与失败。变更过的输入单列，不把补齐观察资源误说成模型更聪明。

存储缺口与旧 Cookie 反例必须有资源/步骤充分的正确对照；充分证据不误报、已确认 Bug 不丢失、清理不改结论同样是退出条件。统计每类失误，不以单一总通过率掩盖严重的无依据通过。未达到判据则修复受影响部分并保留首轮失败，重跑必要对照；不无止境运行到凑够通过样本。

### 历史矩阵

读取 #95、scenario-design-quality 与 code-understanding 的现有驱动，按最新单向交接校正旧 draft 输入。固定八类规划与至少四组 Reviewer 工件，两版本各三次，基准规模为 72 个案例运行；不把它等同于 72 个完整现场 Run 或准确 API 请求数。

优先复用真实生产 Session、工具和受控证据读取入口；工程 fixture 与模型效果分开。每例给出可追溯的判据复核，AI 复核明确标注。缺独立人工评分时仍为 not_run，不把负责人不在场当成可代填人工评分的授权，也不阻塞可独立完成的工程/live 工作。
