# 项目执行服务器与应用启动 Intent

- 日期：2026-10-05
- 状态：需求评审；本轮先提交既有实现，再制定修改方案，尚未实施本需求。

## 问题

当前服务器资源只保存配置和凭据，项目绑定不参与实际执行。镜像构建和命令容器仍使用罗网所连接的本机 Docker。测试环境地址又是项目就绪的必要条件，操作者必须自行部署应用，才能开展浏览器测试。

这与“选择项目运行服务器，由罗网把固定版本跑起来并测试”的目标不一致。受控文件已经能够加密保存，但尚未注入执行环境；仅增加远程命令不能补齐应用启动、访问、证据和清理的完整流程。

## 期望结果

- 项目实际在绑定服务器的 Docker 中构建、运行和清理；本机是默认执行位置，远程不可用时不暗中回退到本机。
- 支持单应用和常见 Docker Compose 多服务项目，用户无需为接入罗网重写成单容器。
- 罗网启动项目时自动提供本次 Run 的可访问地址；已有非生产环境和不需要 Web 服务的仓库仍可测试。
- 受控配置文件可安全用于本次运行，源码、服务、数据卷、凭据、证据和清理都能追溯到具体项目及请求/Run。
- 取消、控制端重启或服务器断线后，能够核对实际资源，明确报告残留与未知状态。

## 本轮负责人补充

- 2026-10-05：对应服务器内部运行各自的 Docker，不把所有项目容器集中到罗网本机。
- 2026-10-05：Compose 在项目中很常见，首版纳入 Compose 支持；不采用先排除 Compose 的范围建议。
- 2026-10-06：当前是单管理员自部署场景，执行服务器和模型均受信任。优先兼容普通项目的 Compose、项目脚本和容器内 Shell；不为恶意租户或恶意模型继续扩展命令白名单和自定义 Compose 子集。
- 2026-10-06：简化不开放宿主机 Shell，也不原样透传 Compose。服务器、Run 容器、目录、动态端口、资源归属、取消和清理由罗网继续控制。

## 影响与约束

影响服务器资源、项目配置与接入、镜像准备、任务快照、调度、Run 生命周期、浏览器/HTTP、Secret 注入、恢复及历史展示。保留现有单管理员、受信任仓库、固定目标提交、角色隔离、场景 patch 权限和报告归档边界。

已有项目与历史结果必须保留。新默认行为不能让升级后的已有项目自动变成由罗网部署，也不能把旧的服务器绑定误记为过去真实使用过远程执行。

## 非目标

- Beta/生产发布、固定域名、长期托管和部署回滚。
- 多控制端分布式调度、Kubernetes、常驻远程 Worker 或恶意租户沙箱。
- 自动创建云主机、替用户安装远程 Docker、修改远程防火墙或开放公网端口。
- 自动迁移外部数据库、凭据或生产数据，或无授权建立新的真实验收目标。

## 待确定的取舍

严格全局并发上限、远端执行未知时不释放占用、故障时其他服务器始终能启动，这三项不能同时保证。建议首版保持前两项，对第三项承诺“有剩余名额时继续”；若需要更强可用性，另行确认全局上限的定义。该问题不阻碍本轮形成可审阅计划。
