# 选定场景期望与结论一致性 Spec

## 行为

- Main 的既有 plan.md 摘要保留选定场景必要期望的原意，并交代验证方式或缺口。工具不可用不是缩减已批准期望的授权；限制段落不是豁免。
- Runner 的观察必须支持原期望，而不是另一个较弱命题。必要期望无法判断时，该场景 blocked；已证实的成功、产品失败仍保留，不把未验证说成产品缺陷。
- Reviewer 独立检查计划是否删弱期望、执行是否偷换验证。同一场景的必要验证缺失不能标 passed 后仅附备注；其他充分验证的场景可以 passed。缺少必要摘要时明确不足，不默认同意计划。
- 最终 Main 只依据 plan/review 汇总，不回读执行或证据。当审核明确承认必要期望未验证却仍标 passed 时，以已有未消解缺口形成 blocked 并指出矛盾，不猜测新期望或抹掉已确认 Bug。
- 额外诊断、重复截图等不影响期望成立的辅助记录不足，只需说明限制，不自动阻塞。仍由模型理解必要性与证据含义，Harness 的结构、安全和完整性职责不变。

## 固定场景原文输入（第二阶段）

- 复用正式Runner开始前的场景读取和执行清单校验；只冻结清单选中的approved场景全文，保持清单顺序。源为不可变target及已验证、已应用的场景patch，不按关键词摘取期望。
- 原文作为Reviewer专属动态上下文中的内存只读视图，附target、patch SHA-256及正文SHA-256；不新增交接文件、报告字段、数据库事实表或仓库/数据库工具。最终Main仍只读plan/review，不获得原文输入。初始化侦察不产生正式快照，候选验证才冻结；需场景审批的特殊短Run不启动Reviewer。
- 冻结后的正文不随Runner操作、后续patch验证清理工作树而改变。空清单对应明确空快照，不等同缺失；大小上限为256KiB（输入及序列化后的快照均检查），超限不得截断伪装完整。
- 沿用现有Secret脱敏；正文变更标redacted，同时保留原始与实际交付正文的不同hash。身份字段无法安全提供、无效文本、超限或Secret读取失败时不交付快照并记录阻塞，不降级为只信Main摘要。正文脱敏是否影响必要判断由Reviewer说明；场景文本不能授权工具、Secret访问或改变角色职责。
- Reviewer以固定原文核对Main摘要与运行证据。Harness只保证输入身份、范围、安全及完整性，不按原文关键词判业务结果。

## 验收与限制

工程检查证明资源能够加载、角色隔离和既有协议未破坏，不证明模型一定遵循指令。

第一阶段以原 Run 的冻结计划、执行和16份原始证据进行一次候选 Reviewer/最终 Main 双 Session 回放，使用原生 Vision low / Flash low。不补入事后数据库核查或原审核未见的场景正文，不修改上游工件，不执行 Runner、浏览器业务操作、清理或归档。运行上下文与本地只读证据传输由驱动重建，不声称是原生 HTTP wire 的逐字重放。

评估是否拒绝较弱验证、结论与必要缺口一致，以及是否把无关截图裁切误作产品失败。保留失败与不确定性；本轮回放不证明规划/Runner 的新指令已在真实执行中有效，不代表完整模型质量通过。第一阶段Reviewer仍依赖Main的摘要，预算对照虽完整交付但未达到语义目标。第二阶段必须独立验证固定原文输入：工程覆盖清单范围、合法patch、初始化、工作树变化、脱敏/超限/缺失、角色隔离；再做一次新条件下的受控回放，只额外提供原固定版本场景正文，不加入事后运行证据。不把这次新条件冒称第一阶段指令已通过。
