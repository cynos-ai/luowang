# 代码深读与测试判断 Spec

- 版本：v0.6.0。
- 状态：实现规格；2026-09-23 按负责人授权编写并开始分阶段实施，完成范围见 [plan](plan.md)，版本尚未发布。
- 输入：[intent](intent.md)。参考 engineer onboard 的固定提交与取舍见 intent。
- 发布边界：单操作者、单仓库；不依赖 v0.6.1 多项目改造，不提前增加项目表或项目切换接口。

## 1. 与已有规格的关系

本 Spec 补充 Main 规划和初始化的代码理解方法、读取事实及交接规则。覆盖 production-closure 中内置资源清单固定不变的限制，扩充一项方法资源；仍不启用 Pi Skills 自动发现。这里的“内置 Skill”指罗网发布物内的一套方法，运行时沿用 Built-in Role Instructions 加载机制。

继续遵循 scenario-design-quality 的业务期望与场景维护规则、model-semantic-decisions 的语义判断边界、single-handoff 的四/六/三 Session 和最终 Main 输入边界，以及 screenshot-capture-integrity 的现场截图与事后审核要求。现有 PROJECT.md 的所有权、Git 工件范围、场景状态和归档权限不变。

## 2. 内置方法与角色范围

新增 `resources/agent-roles/code-understanding.md`，使用现有固定 ID、格式版本、应用版本和 SHA-256 记录机制。构建复制到 `dist/resources/agent-roles/`，quality/runtime 镜像均包含此资源。

| Session | 使用方式 |
| --- | --- |
| 普通 Main 规划 | 完整加载代码深读方法，按固定变更范围聚焦阅读 |
| 初始化静态 Main | 完整加载，建立初始业务理解及侦察需求 |
| 初始化候选 Main | 完整加载，结合 plan/execution 补读并形成正式候选 |
| Runner | 不加载深读方法；根据计划执行或侦察，保留原有受控工具 |
| Reviewer | 不加载深读方法；审核指令补充来源、阅读范围和期望冲突检查 |
| 最终 Main | 不加载深读方法；仍只据 plan/review 汇总，不重新读代码审核 |

资源在 Session 创建前确定性加载；缺失、为空、标记错误、符号链接或不可读时，该 Session 不启动。错误不含本机敏感路径，不回退到旧指令或其他 Skill。Run 的 Session 元数据记录实际加载资源的版本与哈希。

不增加第四组 Agent 配置，不增加模型 Session，不提供任意 Skill 路径或用户上传入口。`skills=[]`、`noSkills=true`、`noContextFiles=true` 等隔离设置保留。目标仓库文件只作为受控数据读取，不能变成系统指令或扩大工具权限；本变更不开放目标 AGENTS.md 自动加载。

## 3. 深读方法

### 3.1 初始化

1. 固定仓库、target_commit 和本次请求，先读取项目理解、相关规格、构建/测试配置及入口，辨明项目类型和可见范围。
2. 从入口追向真正拥有业务规则的模块：处理逻辑、权限、共享状态、持久化、异步任务及外部依赖。入口、路由表和目录只用于定位，不单独作为“理解业务”的依据。
3. 按项目重要行为组织跨文件流程，说明角色、前置状态、正常/拒绝路径、副作用及风险。项目存在某层才分析某层，不套固定技术栈模板。
4. 将已确认契约、实现事实、测试线索、待确认期望分开；已有文档与实现冲突时记录双方来源，不直接宣布规格过时。
5. 从实际配置和测试发现可用的验证方法与诊断来源。脚本存在不等于运行成功，CI 配置存在不等于当前目标环境已就绪。
6. 静态 Main 在 plan 中留下理解、缺口及低风险侦察安排；侦察 Runner 执行后，候选 Main 从 plan/execution 接收事实，必要时补读同一 target，再生成或复用场景。

### 3.2 日常维护

使用固定 base/target 的变化清单和 diff，追踪与变化相关的调用方、共享规则、状态和依赖。删除和 rename 分别核对旧、新路径；无 base、空变化、读取失败和不可读内容不能混为“无需维护”。

每项实质性维护保留“变化依据 → 业务契约或风险 → 已有场景 → 维护决定”。纯重构优先复用，满足既有契约的 Bug 修复不放宽期望，新能力补覆盖，明确废弃使用 deprecated。不得仅按文件扩展名、diff 大小或搜索命中数判断风险。

深度由本次业务问题和风险决定。允许大文件分页、定位后局部精读，不规定最低文件数、流程数或全仓阅读率。未读范围要说明对判断的影响；预算耗尽或证据不足不能被描述为完整理解。对可能改变结论的必要缺口，沿用既有 blocked/draft 规则；非必要缺口不自动阻塞全部测试。

## 4. 客观读取事实

### 4.1 产生位置和内容

复用固定版本读取入口 `read_target_file`、`read_target_file_version`、`read_target_diff`、`list_target_files`、`list_target_changes`、`search_target_files`。由 Harness 在工具返回处记录读取回执，模型不能提交或修改回执。读取事实表示内容成功返回给调用方，不表示模型理解正确。

每条回执包含：Run/Session/阶段、工具调用标识、仓库身份、固定提交（diff 使用 base/target 对）、受控相对路径或操作范围、内容类别、实际返回范围、截断/续读状态、成功或固定错误类别。成功文本读取附可核验的内容哈希；错误回执不保存原始错误或敏感输入。

文件内容覆盖按同一仓库、提交、路径、内容身份及返回的 UTF-8 字节区间计算，区间用半开区间表示。重复页不重复计数，乱序页可合并，存在空洞不能声明全文已读。分页游标必须绑定上述对象，不允许拿另一文件或版本的游标续读。空文件的成功读取与读取失败不同。

覆盖范围只针对允许返回的文本；发生脱敏时明确标记，不声明已读被隐去的原文。分页采用同一受控文本对象的坐标和内容身份，不能混用原文字节位置与脱敏后长度；无法确认映射或总范围时不得标为全文已读。

列文件名和仅返回路径的搜索不计为文件正文已读；内部扫描了文件但没有把正文返回给模型，也不计正文已读。diff 完整读取不等于文件完整读取。搜索达到上限、跳过大文件或部分文件不可读时必须返回相应范围限制，不能将没有命中夸大为全仓没有相关逻辑。

### 4.2 复用现有记录与安全边界

回执复用 Run/Session 的本地受控记录机制，不作为新增正式报告或长期资产上传目标 Git，不新建全局代码理解库。回执不保存大段源码、Secret、绝对路径或任意原始搜索输入；后续查询只返回已验证的脱敏元数据。超出受控响应限额必须分页或明确截断，不能静默遗漏后仍标完整。

不扩展任意文件读取能力。敏感路径、目录越界、symlink、submodule、二进制及不可用版本仍按现有策略拒绝并保留固定失败类别。回执写入失败时该调用不得宣称存在可复核回执，也不能交付未登记的成功结果；采用现有工具错误及规划修正路径。

## 5. 计划交付与独立审核

### 5.1 语义分析

理解结论留在现有 `plan.md`，按生成语言表达：项目或变更范围、关键业务流程、依据与冲突、维护理由、可用验证及缺口。固定 `execution_scenarios` 和 `scenario_review_summary` 继续按已有协议使用，不引入 catalog、suite、能力台账或新的场景 frontmatter。

初始化候选 Main 更新同一个 plan，保留前序侦察及阅读来源，并标明哪些是前序阶段事实、哪些是自己补读；不能把“已读上一阶段摘要”写成“已读全部源码”。v0.6.0 不复用跨 Run 理解缓存；历史报告可以提供线索，但当前目标的关键依据要重新确认。

### 5.2 引用校验

`write_plan` 增加必填的结构化 `sourceReferences` 数组，用来声明本次分析引用的受控读取范围，每个元素包含 `receiptId` 和 `coverage`（`returned-range | full-file`）。空数组允许提交有明确缺口的计划，不强制伪造阅读或场景。

Harness 只核验回执真实存在、归属当前 Run/允许阶段、读取成功及覆盖声明成立；`full-file` 必须由本次引用集合中同一文件固定版本的正文返回区间完整支持，多页读取须列出参与覆盖计算的各页回执。不得使用另一个 Run、搜索路径清单或仅 diff 的回执冒充全文。初始化可引用此前 Main 的回执，仍保留原 Session 归属。引用被拒时不覆盖上一个有效 plan，沿用同 Session 的有界修正机制。

有效 plan 与其引用集合对应同一次成功提交，不能出现新 plan 搭配旧引用。完整集合由 Harness 持久保存；正文不必重复列全部回执。不能用正则检查正文“理解充分”或由文件数量决定测试结果。

### 5.3 各角色可见内容

Main 与 Reviewer 通过受控 `query_source_reads` 查询当前 Run 的回执，带分页及明确的文件/阶段范围。查询不接受任意仓库、提交或本机路径，不开放源码重读。Reviewer 可查看成功 plan 的引用及对应回执，并结合固定场景原文、plan、execution 与既有运行证据独立审核。

回执可以证明引用来源和阅读范围，不能证明调用链解释或业务期望正确。Reviewer 对计划自相矛盾、期望缺少依据、跳过关键验证等作语义判断；仅有路径和哈希不能支撑功能通过。需要进一步源码才能确认但当前角色无权取得时，明确未确认，不自行补造结论或扩大权限。

最终 Main 不获得回执查询或源码工具，只保留 plan/review 中已成立的结论、来源归属和限制。人工场景审核路径继续只交付 patch/report，必要理解摘要进入既有安全摘要区；不为本变更开放额外工件或等待审批的 Session。

## 6. 效果评测与发布条件

工程验收验证资源来源、读取回执、引用校验、权限和交接。真实模型评测另行比较 v0.5.0 基线与 v0.6.0 候选，使用相同输入快照、模型配置、预算规则和预先冻结的判分依据。

八类样本：缺少项目理解文档的初始化、纯重构、满足既有契约的 Bug 修复、新能力、权限/持久化变化、明确废弃、规格与实现冲突、测试条件不足。每类至少三次配对运行；保存全部尝试，不仅挑通过样本。正确维护决定可以有等价表述和拆分，不按场景数量评分。

必须分别报告关键风险遗漏、无依据/被弱化的期望、无谓场景变更、来源归属错误及请求数、Token、耗时。候选不得引入关键错误期望或错误通过；关键风险遗漏和无谓变更不得劣于基线。发布为质量改进需要在预先固定的指标上获得实测改善；无改善或指标冲突时如实记录并调查，不能仅凭工程通过宣称效果提升。

模型对照、人工盲评和实际联合 Run 分开报告。独立 AI 可以辅助逐项核对，但 `humanScoring` 只有真实人工评分时才可标完成。发布前汇总全部验证与未完成项交负责人审阅，不新增产品 Run 的发布门禁。

## 7. 验收条件

| ID | 验收要求 |
| --- | --- |
| AC-CU-01 | 内置方法仅进入规定的 Main Session，版本哈希可追溯；缺失资源失败，外部 Skill 不被加载 |
| AC-CU-02 | 固定提交的正文、diff、搜索与目录回执类别正确；失败、空内容、截断不混淆 |
| AC-CU-03 | 分页、重复页、乱序页、缺页与跨对象游标正确处理，部分读取不冒充全文 |
| AC-CU-04 | sourceReferences 校验 Run/阶段/成功/范围；伪造引用拒绝且保留原有效计划 |
| AC-CU-05 | 初始化两次 Main 保留前序归属；普通四、初始化六、场景审核三 Session 不变 |
| AC-CU-06 | Reviewer 只查询本 Run 受控回执，最终 Main 不获得源码或回执工具；特殊两工件边界不变 |
| AC-CU-07 | 语义对照覆盖八类三次配对，按冻结标准报告改善、不退化和全部失败结果 |
| AC-CU-08 | Secret/路径保护、真实截图、证据审核、清理和归档完整回归通过 |
| AC-CU-09 | 干净 quality/runtime 构建、完整 local、真实联合验收及最终版本标签检查分别完成 |

## 8. 明确不包含

多项目接口与迁移、跨 Run 理解缓存、通用 Skill 平台、自动改写项目理解/工程规范、LSP 或向量数据库基础设施、任意代码执行权限扩展。v0.6.0 可独立发布后，才进入 [v0.6.1 多项目计划](../luowang-multi-project/plan.md)。
