# 罗网（LuoWang）场景测试 Harness MVP Intent

- 状态：MVP Baseline v0.1
- 关联规格：[spec.md](./spec.md)
- 实现计划：[plan.md](./plan.md)
- 项目定位：AI Scenario Testing Harness
- 正式仓库：公开的 `cynos-ai/luowang`
- 许可证：GNU Affero General Public License v3.0（`AGPL-3.0`）

## 1. 当前问题

AI 参与的软件交付已经能生成需求和修改代码，但缺少一个独立、持续运行且以业务场景为中心的测试系统。现有测试通常分散在代码、临时 Agent 对话、人工操作和一次性报告中，导致：

- 项目缺少可随需求和缺陷持续演进的长期场景资产；
- 新提交到来后，难以基于需求、累计变更和历史结果判断真正需要验证的范围；
- 测试执行、证据、初步结论和独立审核没有稳定的交接边界；
- 场景、正式报告、详细运行记录和 GitHub Issue 之间缺少可追溯关系；
- 测试受阻或发现多个 Bug 时，测试进度容易被错误推进或丢失事实；
- 环境凭据和高权限测试能力缺少统一、可审计的承载位置。

## 2. 期望结果

建立一个可独立部署的“罗网”场景测试 Harness，使操作者能够针对一个目标项目持续完成以下闭环：

1. 从项目理解、需求、代码、运行行为和历史结果中建立并维护少量高价值场景；
2. 在新提交、定时任务或人工请求到来时，确定本次需要验证的场景和理由；
3. 在固定目标版本上执行测试并保留关键过程与证据；
4. 由与执行上下文隔离的 Reviewer 独立审核结论；
5. 形成长期可读、可追溯的正式报告；
6. 将确认的不同产品 Bug 分别创建或关联到 GitHub Issue；
7. 只有在报告、Issue 和归档条件真实满足后，才推进罗网记录的测试目标；
8. 通过一个长期运行的控制台查看配置、状态、场景、运行记录、证据和归档结果。

MVP 成功的核心不是场景数量或代码覆盖率，而是形成一个**最小可信、可以重复运行、不会伪造完成状态**的场景测试闭环。

## 3. 受影响的人和系统

### 3.1 人

- **项目负责人/测试操作者**：配置罗网、触发测试、查看结果并处理需要人工审核的场景变更；
- **开发和需求协作者**：通过目标仓库中的需求、代码、报告和 GitHub Issue 获得测试反馈，但不被罗网直接调度；
- **目标项目用户**：间接受益于围绕真实业务结果建立的回归验证。

### 3.2 系统

- 当前唯一目标 GitHub 仓库及其场景测试分支；
- 该仓库对应的测试或预发布环境；
- 模型 Provider 和独立的 Main、Runner、Reviewer 会话；
- 浏览器测试能力、对象存储和本地持久化存储；
- GitHub Pull Request 与 Issue。

## 4. 约束

- 罗网必须独立于写需求、写代码和修复 Bug 的 Agent，不自动修改产品代码，也不调度开发 Agent；
- MVP 为单租户、单目标仓库、单场景测试分支、单测试环境、单实例顺序执行；
- 项目源码公开托管在 GitHub `cynos-ai` 组织下，采用 AGPL-3.0；允许商业使用，但要求分发衍生作品以及通过网络提供服务的修改版按 AGPL 提供完整对应源码；
- `main` 是正式发布分支，`develop` 是开发集成分支，功能和缺陷使用短生命周期分支与 Pull Request；
- 罗网项目仓库不作为 Harness 的目标仓库；MVP 验收使用独立样例仓库和独立本地或非生产样例应用；
- 场景和正式 Markdown 报告以目标项目 Git 为长期事实源；详细运行记录、配置和 Secret 不写入目标项目；
- Runner 的执行结论必须经过独立 Reviewer 审核，不能只相信执行 Agent 的自述；
- 测试范围由 AI 基于需求、变更、历史事实和场景语义判断，不建立手工维护的测试套件；
- 受阻、执行中断、证据缺失、清理失败或归档失败不得伪装成通过；
- 空数据库的管理员密码只从 `LUOWANG_ADMIN_PASSWORD` 初始化，不提供匿名设密或公开默认密码，已有密码不能被环境变量覆盖；
- Main 只能提出场景目录内的变更；Archiver 只能原样发布已验证场景 patch，并只为当前 Run 新增正式报告，不得改写产品、需求或历史报告；
- 凭据按最小权限暴露，不能出现在 API 响应、日志、报告或被测命令的继承环境中；
- MVP 只连接操作者信任的仓库和非生产测试环境，不把单容器执行视为恶意代码安全沙箱；
- 优先使用 Pi、skills、提示词和现有协议能力，只在真实需要出现后增加约束或抽象。

## 5. 明确不做

MVP 不负责：

- 多用户权限、多租户、多仓库或多测试环境管理；
- 并发执行、worker 池或通用工作流引擎；
- 发布 gate；
- 自动修复产品代码、解决合并冲突、生成修复需求或通知开发 Agent；
- 从其他开发分支推断整体测试状态；
- 建立复杂场景状态机、手工测试套件、长期能力图或重型 artifact 模型；
- 保存完整 Agent 对话、隐藏推理或原始工具结果；
- 在生产环境或不可信仓库中执行测试；
- 使用罗网实例测试另一个罗网实例，或为此建立双实例架构。

## 6. 尚待确认的问题

当前没有阻塞 MVP 规格和分阶段实现计划的产品问题。以下方向明确留到 MVP 验证后再决定，不应在本次实现中预设：

- 演进为单平台多仓库，还是继续保持每个仓库独立部署；
- 是否引入容器级 worker 以支持环境隔离和并行；
- 是否需要通用 MCP Server、专用 Vision Agent 或外部 Secret Store；
- 是否增加新的需求级工件、场景目录分片或更严格的文件所有权机制。
