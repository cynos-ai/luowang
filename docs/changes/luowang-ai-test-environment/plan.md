## 1. 为什么改

当前执行能力已经有了，但配置入口仍像基础设施表单。用户接入项目时要先理解启动方式、Dockerfile、Compose 服务和数据连接，这些正是罗网应通过读取代码完成的工作。

这次把用户要决定的事项与罗网要推导的事项分开：用户选服务器、运行方式、测试数据和触发规则；罗网生成并验证可执行环境。高级编辑保留，普通流程不再要求手填所有启动字段。

## 2. 基线与已存在的改动

必须包含 `feat/execution-server-runtime` 的完整当前基线：HEAD 为 `6e94f89`，执行服务器改造及模型/品牌前置已经在其历史中；不能从旧 develop 直接开始。

工作树还有本轮之前尚未提交的项目删除、成功状态配色和全局文案清理。本方案只新增本目录三份文档及其审阅内容，没有把这些已有工作重做、回退或冒充本方案实现。实施者需先核对/保存完整工作树基线，不能只 checkout HEAD 后丢掉这些改动。

## 4. 实施阶段

### Phase 0：收敛规格和兼容规则

- 定时语义、文件/脚本初始化和用户点击更新策略均已确认；先选实际试用项目需要的文件格式和初始化步骤。
- 数据准备不再等待备份平台选型，按需直接用现成导入工具；源库连接、自动导出、同步和五引擎专用复制适配器后置。
- 列出字段/存储/迁移差异，区分普通定义、Secret 引用、SQL 内容与本次运行事实。
- 确定生成任务与正常四 Session Run 的边界，以及固定 target 后实际定义的冻结位置。
- 对旧配置逐项说明保留、映射与显式转换，不静默改变已启用自动任务。
- 退出：行为与验收要求稳定，开始增量实现。

### Phase 1：页面重组与文件上传

- 基本资料保留 GitHub 授权；运行环境集中运行方式和服务器；网址仅 external 显示/必填。
- 测试数据聚合账号和后续数据资源，不把现有“外部数据库说明”改名后假装能连接数据库。
- 触发页显示两个独立卡片；未接通的能力不放可点击的假按钮。
- 配置文件增加上传，默认原文件名及根目录，目录可编辑；高级编辑保留目标服务。
- 保留旧链接入口与未保存修改保护，复用 NumberInput、SelectBox、Dialog、Message。
- 验证：真实浏览器的上传、保存/失败、三种运行方式、旧链接、三个视口和键盘行为。
- 本阶段仅完成现有能力的入口改进，不能声称 AI 准备或数据库同步完成。

### Phase 2：AI 生成定义与执行链集成

- 从固定代码版本读取足够材料，复用已配置测试组长模型，不把连接密码或配置文件内容塞进 Prompt。
- 首次生成、重新生成和失败后的修正均由配置页按钮触发；相关变化提醒复用正常分析结果，不自动调用配置生成或改写定义。
- 生成自己的测试 Dockerfile、必要 Compose、启动/健康/测试位置和数据初始化引用；对缺项给真实结果。
- 保存来源、定义摘要、人工覆盖和有界生成/修正记录。重新生成有差异查看，不覆盖人工修改。
- 在已有准备流程物化生成文件；生成文件、产品源码、场景 patch、运行秘密保持各自职责。
- 缓存摘要包含实际构建定义；同一产品提交及定义跨 Run 可复用，数据文件变化不应重建相同产品镜像。
- 配置生成与启动验证分开，验证使用所选执行服务器并计入准备容量。
- 验证：用户发起后，一个无 Dockerfile 的应用与一个带数据库的项目均生成可运行定义；相关变化只提醒、未点击不更新，正常 Shell、取消、失败和资源回收仍可用。

### Phase 3：测试数据初始化

- 支持多个数据文件及必要说明，记录归属、版本、摘要、大小和内容引用；二进制文件不经过 UTF-8 配置文本入口。
- AI 在用户发起生成时选择现成导入工具或生成初始化脚本，脚本/目标服务/文件位置/顺序随启动定义一起查看、编辑、保存和冻结。
- 在所选服务器、本 Run 容器内准备文件并执行保存步骤；不增加源库连接管理或动态模型导入旁路。
- 按项目顺序完成依赖准备 → 初始化 → 应用健康 → 测试；初始化失败停止后续测试，不伪装为空库成功。
- 使用有界上传/传输，复用取消和 Run owner 清理；上传原件保留，运行副本和临时资源回收。
- 首轮证明：一个实际项目用 `.sql` 或其实际数据文件成功初始化，读取预期记录；覆盖脚本失败、取消、多个文件映射及两个 Run 数据不继承。不以五引擎全部导出/恢复矩阵作为试用前提；其他格式据实标记未验证。

### Phase 4：测试触发

- 普通数字+单位对应真实间隔，支持秒；高级 Cron 沿用 UTC，不用 Cron 近似任意间隔。
- 提交触发和定时检查共用待测判断；普通触发没有待测批次时不调用模型或启动环境，显式重测及初始化保留。
- 核对上次归档推进目标、lastSeen 和已有任务的职责；观察/入队不冒充已测试，不每个 tick 重试失败任务。
- 使用现有队列与同项目互斥；暂停、忙碌、重启和失败期间不产生无限积压或重复认领。
- 保留旧 Cron 的“无新批次不运行”语义；普通人工/API 检查与旧强制运行入口的兼容映射明确记录，不静默改已有请求。
- 验证：时钟控制测试和持久重启测试，涵盖开关、所有单位、Cron、重复 tick、占用和 no_change 场景。

### Phase 5：同一候选的完整验收

- 运行与改动匹配的类型、lint、格式、单测、构建及浏览器回归；在固定 Docker quality/runtime 环境执行。
- 本机完整流程：接入 → 生成 → 上传/数据准备 → 启动 → 真实测试 → 报告 → 关闭环境。
- 一台真实远程服务器验证同一流程及停止/清理；不先扩张到双服务器故障矩阵。
- 优先选一个实际试用项目验证没有 Dockerfile 时的生成、配置上传和文件/seed 初始化；其他项目/格式按实际证明列出，不冒充全部支持。
- 复核旧手动定义、三个运行方式、历史 Run、文件/Secret 归属及迁移回退。
- 把零模型 fixture、模型生成、模型测试、远程流程和迁移证明分别记录。未提供资源的部分写未运行，不宣称整体验收通过。
- 模型/服务器/数据库的真实验收资源在实施阶段核对；本轮方案整理不调用模型，不连接用户数据库或创建测试环境。

### 7.2 可以明显节省时间的取舍

- **先跑通，再全面重组页面**：Phase 1–5 目前混合完整产品范围。首个交付在现有设置页补生成/更新、编辑保存和上传入口，接通构建、初始化、健康和完整 Run；六分组的完整整理、触发编辑器与广泛样式回归随后完成。新增入口仍须有错误反馈、键盘和基本视口检查。
- **新的 AI 输出统一为 Compose**：单应用也是单 service Compose，多依赖沿用同一输出形态与初始化路径；既有手动单容器继续兼容。这样不用首轮同时扩展两套生成文件消费契约，Spec 已同步。
- **配置更新不做智能合并系统**：先提供旧/新结果对照、用户编辑和明确应用/保存。生成来源与摘要保留；不把版本分支、自动合并、自动修复循环或复杂输入指纹识别作为首轮前置。变化提醒复用现有分析，启动失败给出诊断和更新按钮，不额外启动模型监听任务。
- **三种模式保留，但不顺带扩展它们**：本版 AI 启动和多服务文件初始化优先接 `managed`。Spec §3.1 的 repository-only “有依赖容器时也可准备”超出现有 `run-runtime-factory.ts:53` 的非 managed 早返回，应明确后置或单列工作，不把它当成已能复用的能力；external 不自动操作既有应用数据库。
- **触发保留原语义，小步改入口**：Git/Cron 已共用 Poller，普通检查与显式重测明确区分即可。保留旧请求、推进和失败恢复规则；数字/单位编辑复用已有时钟与调度，不重建队列，不为本版扩大失败自动重试策略。
- **本机试用与远程证明分开记录**：先交付实际本机项目，远程完成工程接入后以一台真实 SSH 服务器验证；没有实机资源时列为未验收，不阻止本机试用，也不能将远程标为通过。完整远程证明仍属于原功能的验收要求。

### 7.3 建议的最短交付路径

1. 选定一个真实试用项目、必要数据文件和执行服务器；若首轮本机，不先等待远程资源。
2. 用户点击生成，AI 读取固定源码，返回现有 runtime 字段、生成文件和初始化脚本；用户编辑后保存。首次固定源码复用 `resolveProjectImageCommit`：已有场景分支取其 HEAD，没有则取经核验仓库默认分支；生成不私自创建场景分支，也不推进测试。
3. 已保存定义进入当前准备链，构建只使用固定产品源码和生成的构建定义；数据/凭据在运行阶段准备。测试执行 service、源码目录和初始化工具一并确认。
4. 实际完成数据初始化 → 应用健康 → 原四 Session 测试 → 正式报告归档 → Run owner 清理；已有场景 patch 导致环境重建时再按保存步骤初始化。
5. 用同 SHA 的生成文件修改、初始化失败/取消、连续两次数据隔离证明核心行为。随后完成设置分组与触发编辑，并在同一候选上验证一台真实 SSH 服务器。

开发投入相对排序：生成定义接入和初始化生命周期为高；字节文件上传与版本引用为中；页面字段/导航整理和触发控件为较低。没有实施及真实项目验证前不给精确工期承诺，避免将“AI 能写脚本”当成已经接通执行流程。
