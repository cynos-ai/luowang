# AI 测试环境方案

- 日期：2026-10-07
- 状态：已确认并接入工程；本机检查与真实项目/远程验收以 Plan 为准
- 目标与边界见 [Intent](intent.md)，实施顺序见 [Plan](plan.md)

## 1. 实施前核对的现状

| 项目 | 当前实际行为 | 本次需要补齐 |
| --- | --- | --- |
| 运行位置 | 本机或项目绑定的 SSH 服务器使用自己的 Docker | 继续复用，不另建 Worker |
| 运行模式 | `managed`、`external`、`repository-only` 已实现 | 用运行方式组织页面和字段 |
| 自行启动 | 能执行已填写的单容器或 Compose 定义 | 缺少读取代码并生成运行定义的 owner |
| Dockerfile | 可指定目标仓库内文件；留空使用内置执行镜像 | 能生成罗网自己的应用/测试构建定义 |
| Compose | 原生 `docker compose config` 解析后规范化运行资源 | 接收生成的定义，继续使用现有解析和运行器 |
| 测试环境网址 | managed 使用本 Run 动态地址，external 使用保存的 baseUrl | 不再让所有模式都面对网址表单 |
| 数据库 | Compose 可启动依赖服务和 Run 专属卷 | 接入上传数据文件及初始化命令/脚本；本版不实现源库连接和导出 |
| 测试账号 | 项目 Secret Store 已有账号、密码、清理 Token | 与其他测试数据一起组织；GitHub Token 移回仓库连接 |
| 外部数据库说明 | 只是普通说明字段 | 不能把它当作已经支持数据库连接或同步 |
| 配置文件 | 加密保存 UTF-8 内容并在运行阶段注入；单文件上限 256 KiB | 增加上传与默认根目录，减少手填服务名 |
| 自动触发 | Git 轮询与五字段 Cron 最终都调用 Git Poller，无新提交时不运行 | 保留待测判断，改进触发设置的表达及简单间隔 |

既有 MVP Spec §18.3/18.4 已定义无新批次时 Cron 不运行，以及每项目的上次完成目标。用户于 2026-10-07 确认继续采用这个规则，撤回本方案此前“定时无变化也重测”的建议。

代码仍需区分观察位置与完成位置：`poller.ts` 当前用 `lastSeen ?? progress` 检测新到达的变化；lastSeen 用于检测/去重，不能证明测试已经完成。后续任务范围使用已归档推进位置，待测判断还要核对已排队、执行中、待归档和失败任务。本次是设计核对，没有修改该执行逻辑。

## 2. 项目设置分组

建议使用六个分组，沿用现有共享组件和页面风格：

| 分组 | 用户配置什么 |
| --- | --- |
| 基本资料 | 项目名称、仓库身份、GitHub 授权选择 |
| 测试规则 | 语言、场景维护、场景标签等已有规则 |
| 运行环境 | 运行方式、执行服务器、生成的启动配置或已有网址 |
| 测试数据 | 数据文件、初始化脚本、测试账号、其他测试所需凭据、可选清理设置 |
| 触发规则 | 新提交触发、定时触发 |
| 配置文件 | 上传文件、目标文件名与目录、必要时修改内容 |

旧设置 URL 保留兼容入口，不改 projectId 或 UUID 路由。原“测试环境”页的内容合入所属分组，不能只隐藏导航而留下另一份独立表单。

“凭据”不再成为杂物页。GitHub Token 是仓库连接凭据，不是测试数据；管理员密码、模型和对象存储凭据仍属于全局设置。

2026-10-07 页面反馈补充：

- 运行环境使用统一字段网格、间距和独立操作区。服务器/运行方式、启动配置、运行参数和浏览器额外来源按顺序排列；高级字段展开后按钮不随文本框拉伸。
- 文件选择、拖放、更换、大小校验及选中文件状态由共享 `FileUpload` 组件提供，测试数据和配置文件复用。没有已保存文件时不显示空列表或“尚未保存受控文件”。目标路径的默认值和示例放在字段帮助中。
- 测试账号和密码放入同一组，通过一次请求、一次事务保存。留空保留原值，任一写入失败则整体回滚；单独清除仍使用确认操作。可选清理接口地址与授权 Token 放入同一个高级分组；帮助说明其调用用途，不新增清理机制。
- 数据文件页只上传，不要求另行填写文件内容。配置文件上传后可直接保存，文本编辑放在可选展开项中，也保留手动创建文本文件的入口。
- 共享启用开关使用与罗网按钮一致的方形边框和错位阴影，启用时用红底与勾号，未启用时用纸白底与状态文字；保留原生键盘/焦点和 switch 语义。
- 触发规则的启用开关与卡片标题同级，显示已启用/未启用状态，卡片和字段同时反映状态。数字与窄单位选择框紧邻，单位不另设可见标题。定时间隔在未启用时仍展示；填写 Cron 后间隔禁用，清空 Cron 恢复间隔。普通定时触发仍只处理待测批次。

## 3. 运行环境

### 3.1 三种运行方式

| 方式 | 罗网做什么 | 用户需提供什么 |
| --- | --- | --- |
| 罗网启动项目 | 在所选服务器准备并启动应用、依赖和测试工具，再执行测试 | 服务器、必要配置文件和测试数据；普通启动参数由 AI 生成 |
| 使用已有测试环境 | 访问已运行的非生产应用，不负责启动该应用 | 目标网址及需要的账号/访问配置 |
| 只测试仓库内容 | 保留已有独立命令容器，执行仓库测试、脚本；不要求应用网址 | 服务器及已有执行配置；本轮不扩展多服务依赖栈 |

已有网址仅在 external 模式必填。managed 展示本次运行的实际网址，repository-only 不展示应用网址输入。浏览器额外来源、环境备注等放入相应运行方式的高级选项，不因移走网址而丢失这些设置。

external 应用的数据库由该应用自己的部署决定，上传文件不会自动改变已有网站的数据库。本方案的文件初始化首先作用于罗网创建的环境；已有环境的清理/数据准备继续要求明确配置。

### 3.2 AI 生成配置

新项目选择 managed 后，配置页面提供“生成启动配置”操作。用户点击后进入准备流程：固定代码版本，读取启动脚本、依赖、服务结构、迁移/种子脚本及已有运行文件，生成测试用运行定义。选择运行方式、打开页面或自动测试触发本身不调用配置生成模型。

生成内容包括：

- 应用及测试工具需要的 Dockerfile；
- 必要时生成 Compose，包含应用、数据库及其他依赖；
- 安装/构建/启动步骤、源码目录、测试命令执行位置；
- 应用端口、健康检查、服务依赖和启动顺序；
- 配置文件的使用位置、测试数据初始化步骤；
- 尚缺少的用户输入，以及不能确认的项目条件。

新的 AI 生成路径统一输出 Compose；单应用可以只有一个 service，多依赖使用同一契约。已有手动单容器配置保持可用。普通表单不要求用户先选启动类型，生成结果显示应用和依赖摘要，完整 Dockerfile、Compose、命令和目录放在“查看/修改启动配置”中。

AI 默认可以自己生成测试 Dockerfile，不强制采用仓库的生产 Dockerfile。已有 Dockerfile/Compose 可以作为分析材料，也可由用户在高级编辑中明确指定使用。

复用测试组长的模型与来源，不新增角色配置。环境生成只分析构建/启动所需材料，采用低思考预算；模型不支持时沿用现有 SDK 的等级映射。它是准备任务，单独记录模型调用与结果，最长 10 分钟并可停止；正常测试的角色等级、Main/Runner/Reviewer 交接和四个隔离 Session 规则保持不变。

只读页面不触发模型调用。已有项目转换到 AI 准备需显式操作；生成、重新生成和启动探测应有进度、停止与失败反馈。启动失败记录原因并提供用户可点击的修正/更新操作，不在后台自动调用模型修正配置。用户发起的一次生成任务可以做有界校验，结果作为待查看内容，不无限循环或自动覆盖已保存定义。

### 3.3 生成、修改与验证是不同状态

- 生成成功表示定义已生成；应用是否可运行由构建、启动、数据初始化和健康探测证明。
- 不确定时列出缺项，不能填入虚构的服务、账号、端口或“已就绪”。
- 用户可修改生成结果。重新生成先展示差异，不覆盖人工修改或静默切回自动值。
- 已有手动定义保留为手动来源，不在升级或打开页面时改写。
- 生成失败保留可诊断原因和上一份已保存定义，不把失败输出直接变成当前配置。

### 3.4 版本与运行集成

生成文件属于罗网的测试配置，不写入目标 Git 产品树，也不突破 Main 场景 patch 的目录权限。

项目配置保存可复用定义及生成来源；每次请求准备时，结合固定 target、服务器修订、文件/数据资源版本形成实际运行定义。实际定义及摘要随本次任务冻结，不修改已经认领的队列快照或历史 Run。

用户已确认更新策略：配置页点击“更新启动配置”才重新分析/生成。代码版本变化、定时触发、准备/启动失败都不能自行触发配置更新。保存定义继续用于本次固定提交的构建和启动；定义缺失或不可用时给出真实缺项/失败，不在运行中自动补写配置。

AI 在正常的代码理解或运行任务中发现依赖、启动脚本、服务结构等相关变化时，可记录“建议更新启动配置”及具体原因，配置页展示提醒和更新按钮。复用已有分析事实；不为了检测变化每次额外调用一次模型，不增加自动更新任务。用户可暂不更新，提醒不冒充配置已失效；实际构建或启动失败仍如实处理。

人工修改继续保留。用户发起更新后先查看生成结果和差异，再应用/保存，不覆盖人工内容。配置更新只影响后续准备，已认领请求和正在运行的任务继续使用冻结定义。

当前配置快照是不可变的。固定 target 后解析、物化已保存定义时，在现有请求准备/执行上下文记录本次实际定义，不能回写 `config_snapshot_json`，也不能在运行中改共享项目配置或自行调用模型更新它。

生成文件、上下文路径和构建摘要须进入现有缓存核验。产品源码、场景 patch 和运行期文件仍分开；运行秘密和数据库内容不能因生成 Dockerfile 而进入 `COPY . .`。

## 4. 测试数据

### 4.1 本版只做文件和脚本

按用户最新要求缩减：上传数据文件、使用项目已有迁移/seed，或让 AI 生成可编辑的初始化脚本。直连源库、自动导出/在线备份、数据库同步和独立备份平台后置，不要求先接通五种引擎的数据复制才能试用。

测试账号/密码和其他测试凭据继续使用现有 Secret Store。数据文件允许多个，保存名称、用途、版本、摘要、大小和受控内容引用，不增加数据库连接配置页或第二套数据源管理系统。

| 项目依赖 | 文件/脚本的常见用法 |
| --- | --- |
| PostgreSQL / MySQL | 上传 `.sql`，使用对应客户端导入或项目 seed |
| MongoDB | 上传 JSON/JSONL，使用 `mongoimport` 或项目初始化脚本；已有原生备份也可由明确脚本恢复 |
| Redis | 用初始化脚本写入测试键值；已有 RDB 可在专属实例启动前放入数据目录 |
| SQLite | 使用用户准备好的 `.db`/`.sqlite` 文件副本，或导入 `.sql`/执行项目 seed |

这张表是通用文件/脚本入口的使用方式，不是五套专用导出/恢复适配器。文件格式、版本和使用方法由保存的初始化定义决定；不能只凭扩展名宣称任意文件均可导入。未验证的格式明确反馈，不做跨数据库转换或自己解析 BSON/RDB。

SQLite 上传完整的可用数据库文件；从正在运行的库取得一致副本由用户的导出工具完成，本版不实现在线备份。Redis 以本次专属实例或脚本准备数据，不操作外部源实例。

### 4.2 AI 生成步骤，工具实际执行

在用户点击生成/更新启动配置时，AI 根据项目代码、文件名/格式、用途说明和必要的结构材料，选择现成导入工具或生成项目初始化脚本。无需把整份数据库文件送给模型；二进制文件交给对应工具使用，大数据文件不塞进 Prompt。凭据沿用已有引用，不把密码写入生成脚本。

初始化步骤与 Dockerfile/Compose 一起展示、编辑和保存，包含目标 service、文件位置、命令/脚本和执行顺序。运行时执行已冻结的定义，不临时让 AI 自由决定是否跳过导入，不因导入失败自动改配置。

复用现有容器内 Shell/命令能力。罗网负责文件准备、调用脚本、超时/取消、错误反馈和收尾；具体导入使用 `psql`、`mysql`、`mongoimport`、`redis-cli`、SQLite CLI 或项目工具，不自己实现 SQL/备份格式、同步协议和格式转换。

之前调查的 [DBackup](https://github.com/Skyfay/DBackup)、[Portabase](https://github.com/Portabase/portabase) 属于完整备份应用，本版不引入，也不把进一步备份平台选型当作实现前提。若某一步需要现成库，仍优先复用，按实际需要选择。

### 4.3 运行顺序与最小可靠性

每次运行使用固定版本的数据文件副本：准备文件和数据库依赖 → 按定义执行迁移/导入/seed → 核对初始化结果 → 启动或核验应用 → 测试 → 清理本 Run 的临时文件、容器和卷。按项目及工具需要调整先后，例如 Redis RDB 在服务启动前准备，SQLite 文件在应用启动前准备。

默认从初始文件重新创建本 Run 数据，不继承上次测试写入。上传原件不参与测试写入或运行收尾删除。多个文件对应明确的目标和顺序；已配置步骤失败就报告失败，不能默默改成空库测试。无数据文件时可使用项目 seed 或明确的空库。

记录文件版本/摘要、步骤、退出结果和必要的数据读取证明；不是完整数据库审计系统。大文件采用有界上传/传输，大小及耗时上限在实现时确定，不复用配置文件的 256 KiB 限制，不一次塞进配置 JSON。

复用现有准备容量、取消和 Run owner 清理，未确认结束的资源仍保留 unknown/占用。显示真实初始化结果；初始化成功不表示测试通过。先跑通一个实际项目及其需要的数据文件，其他格式逐步验证并据实列出支持情况。

## 5. 测试触发

页面分成两个独立大卡片，各有开关和对应配置：

| 卡片 | 常用控件 | 建议行为 |
| --- | --- | --- |
| 有新提交时测试 | 开关、检查间隔数字、秒/分钟/小时单位 | 发现待测试产品变化后创建请求，继续过滤纯场景/报告提交 |
| 定时检查 | 开关、每 N 秒/分钟/小时/天 | 到时检查待测批次，有则安排，没有则不运行 |

两种方式可以单独或同时启用，使用同一队列、项目互斥和服务器容量。重启、暂停及任务执行期间不积累无限定时请求，不追补每个错过的时间点。

“天”表示固定 24 小时间隔。需要日历时间时，展开高级编辑填写 Cron（沿用现有 UTC 语义）。简单间隔支持秒；不要用五字段 Cron 假装支持秒，也不要用 `*/N` 拼凑任意间隔。

定时间隔和高级 Cron 是同一“定时检查”卡片中的两种计划表达，不能同时暗中生效。保存、切换和关闭后以持久状态为准。

普通触发采用同一流程：触发检查 → 读取本项目已推进目标和当前可测试提交 → 核对待测变化及已有任务 → 有新批次则入队，没有则结束。触发方式只决定何时检查，不表示强制创建 Run。代码无待测变化时，不调用模型、构建或启动测试环境。

- 以上次满足归档推进条件的目标作为下一批 `base_commit`，固定本次 `target_commit`；多条新提交合并为一批，不逐条重复启动。
- 纯场景/报告变化不单独创建自动批次，沿用原规则。
- `passed` 在报告归档后推进；`failed` 在报告归档且 confirmed Bugs 均关联 Issue 后也可推进。完成测试不等于全部通过，不能为已归档的问题每次定时重跑。
- `blocked`、`interrupted`、基础设施失败及未完成归档不推进；已有任务和错误仍可见。不能把 lastSeen 当成已完成，也不能因未推进而每次 tick 无限制重试；沿用既有恢复/人工重试规则，不新增失败重试框架。
- “重测”是用户明确要求重复测试当前版本的独立操作；保留现有重测和首次初始化流程。普通人工/API 检查入口与旧 `manual-current-head` 强制运行语义需明确区分，不静默改变旧接口或已保存请求。

验收须在提交检测和定时入口共用的调用链上证明该行为，不能只验证定时器触发了回调。

## 6. 配置文件

- 提供“上传文件”，保留文本编辑能力。选择后使用原文件名，目标目录默认项目根目录 `.`。
- 用户可以调整文件名、目录和内容；列表显示文件名、目标位置、版本、大小和保存状态。
- 普通表单不要求填写 Compose service。根据生成定义确定使用文件的应用/测试位置；目标服务和具体容器路径放在高级编辑中。
- “项目根目录”是所选项目在运行容器里的源码根，不是宿主机根目录，也不一律等于 `/luowang-source`。生成定义和实际注入必须使用同一映射。
- 保留已有路径、文件冲突、版本与取消规则。首版配置文件延续 UTF-8 文本支持；SQL 上传属于测试数据流程，不能误注入为普通应用配置。
- 上传和内容在受控存储中保存，不写 Git，不进入通用构建镜像，不因为展示文件而返回原有 Secret。
- 上传后可编辑新选文件；编辑已保存内容需重新提供内容，不能为“编辑”新增默认明文回显。

## 7. 保留与不增加的机制

继续使用现有配置、Secret Store、Queue/Coordinator/Dispatcher、原生 Compose、执行 adapter、资源台账、命令服务、浏览器和归档 owner。

新增检查限于定义格式、必要字段、固定版本、资源归属、运行路径和原件/运行副本区分。容器内继续支持普通 Shell 和项目脚本。不扩大命令白名单，不建设恶意模型防护框架，不开放宿主机 Shell。

生成任务和文件/初始化步骤失败应有可用诊断，但不能把原始密码、SQL 数据或包含秘密的 Compose 内容直接写进日志。

## 9. 已确认与仍待审核的事项

### 2026-10-09 配置辅助补齐

- 草案默认展示应用/依赖服务、入口、健康检查、初始化步骤和文件；原始 JSON 与生成文件在高级查看/编辑中保留。更新展示字段和文件变化，不要求用户阅读整段 JSON 才能保存。
- 生成输入包含已保存运行参数、初始化步骤、所选执行端能力及用户补充要求。用户可明确选择携带最近一次环境验证失败信息更新；不会自行修改配置。
- AI 可以提交明确的缺项清单，缺项作为正常准备结果展示，不伪装为模型连接失败；用户补齐后主动重新生成。
- 最新草案和验证结果按项目持久保存。服务重启中断的任务标记中断，不自动继续调用模型；已保存或已放弃的草案不再恢复成未保存编辑。过期草案保存前核对输入，不能覆盖新的人工配置。
- managed 模式提供用户主动触发的“验证环境”：冻结已保存配置、文件版本、执行位置和源码提交，复用正式运行器完成构建、初始化、启动、HTTP 健康检查和清理。逐阶段展示事实，不创建正式 Run、调用测试模型、推进提交或归档报告。
- 验证占用现有服务器容量，并与同项目测试、准备及配置变更互斥；取消、重启和清理不确定时沿用资源恢复机制。只有清理核实完成且所有执行阶段通过才显示验证通过。配置变化后旧结果显示已过期，不冒充当前配置可用。
- 验收覆盖缺项、人工配置更新、草案恢复/放弃/过期、验证取消/失败/清理、共享容量和真实 Docker 启动。真实 AI 生成并启动的项目证明与零模型 fixture 分开记录。

1. **定时语义（已确认）**：到点检查待测任务，有则安排，没有则不运行，沿用已完成目标的推进规则；不增加自动无变化回归。
2. **首版数据范围（已确认并简化）**：常用数据库依赖通过上传文件和现成导入/seed 脚本初始化；先跑通实际项目，不做源库直连、自动导出/同步或五引擎完整复制矩阵。具体规则见 §4。
3. **生成更新策略（已确认）**：用户在配置页点击才生成或更新；AI 感知相关变化只提醒，不能自动更新，人工修改和已冻结任务保留。

三项产品决策及独立审查取舍均已确认。本版优先跑通“上传文件 → 用户生成/保存配置 → 初始化 → 测试”；需要工具时直接复用现成实现，不再等待备份平台选型。实施先接通 managed 与通用文件入口，随后完成设置分组和触发编辑。需求确认不代表工程完成；本机试用和真实远程验收分别记录。
