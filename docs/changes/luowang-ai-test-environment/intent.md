# AI 准备测试环境与项目设置调整

- 关联：[`luowang-execution-server-redesign`](../luowang-execution-server-redesign/spec.md)

## 当前问题

项目设置仍要求操作者填写 Dockerfile、Compose 服务、启动命令、端口等实现细节。虽然罗网已经支持在本机或项目所选远程服务器上启动容器、执行测试，但没有替用户完成这些配置的准备流程。

“测试环境”和“执行环境”并列，用户不知道运行网址何时需要填写。“自动化”混排 Git 检查和 Cron，用户看不出两种触发方式。“凭据”同时放 GitHub Token 和测试账号，又没有数据库、SQL 等测试数据入口。配置文件只能粘贴内容、手填路径和服务名，接入成本较高。

这不是增加几段帮助文字就能解决的问题：页面组织和准备职责需要与实际测试流程一致。

## 期望结果

1. 用户主要选择运行方式、服务器，提供必要的配置文件和初始测试数据。
2. 罗网读取固定版本代码，准备适合该项目的运行定义；普通用户不必先判断单容器或 Compose。
3. 罗网可以使用自己生成的测试 Dockerfile/Compose，不依赖目标项目是否提供 Dockerfile，也不修改目标仓库产品代码。
4. 生成结果可查看、修改和重新生成，人工修改有明确所有权。
5. 自行启动项目时自动提供运行网址；仅使用已有测试环境时要求填写目标网址。
6. 测试使用自己的数据库和数据副本。首版上传数据文件或使用项目 seed 脚本，支持多个文件；直连其他数据库复制初始数据后置。
7. 提交触发和定时触发清楚分开；常用定时设置使用数字和单位，Cron 为高级选项。
8. 配置文件支持上传，默认放在项目根目录，文件名和目标目录可调整。

用户已于 2026-10-07 确认：普通触发只是检查入口，先判断有没有待测试任务，有则安排，没有则不测试。定时到点不重测已完成的相同版本；继续沿用已有提交推进规则，明确的人工重测单独保留。

首版允许项目使用 PostgreSQL、MySQL、MongoDB、Redis、SQLite 等常用依赖；数据初始化通过上传文件和脚本完成。用户希望尽快跑通一版，因此不为五种引擎各建数据源连接、自动导出和同步功能，也不以五引擎完整复制矩阵作为首轮试用前提。

启动配置的生成与更新统一由用户在配置页面点击触发。AI 感知相关变化时提醒用户是否更新，不自动重新生成、修正或替换已保存配置。AI 根据项目、文件类型和用途生成可查看的初始化命令/脚本，执行交给现成导入工具或项目 seed；不自行实现备份格式、数据转换和同步逻辑。

## 范围与约束

- 面向信任项目、服务器和模型的自部署使用者，延续已有执行链和 Secret Store。
- 保留固定提交、Run 资源归属、并发容量、取消、失败反馈和准确清理。这些属于执行可靠性。
- 不增加命令白名单、恶意模型防护体系、宿主机通用 Shell 或新的调度框架。
- 不负责向生产发布项目；不访问生产数据，不将数据源当作可随意修改的测试目标。
- 上传数据原件保留，测试使用本次运行的副本；导入和测试写入发生在本次运行自己的数据库中。
- 不把模型分析成功、配置生成成功或保存成功写成应用启动、数据初始化或测试通过。
- 现有模式和手动配置应继续可用，不因升级自动调用模型、重建环境或改动已有项目。

## 非目标

- 通用发布平台、长期运行环境管理和生产数据库同步。
- 数据库双向同步、持续复制、增量 CDC、跨数据库一致性协议。
- 直连源数据库、自动导出/在线备份和完整备份管理平台，本版均后置。
- 新用户体系、权限体系、Agent 角色体系或第二套 Secret/文件事实源。
- 一次支持所有数据库引擎、所有备份格式和所有项目结构。

## 审核重点

- AI 生成定义如何进入现有准备和运行流程，而不是增加另一条执行旁路。
- 各普通触发入口是否共用待测判断；已完成的提交、已排队任务和上次仅观察到的提交是否正确区分。
- 文件和初始化脚本是否能在选定服务器的实际容器中使用，导入失败是否明确阻止后续测试。
- 新的页面分组是否足够清楚，且没有用“自动”文案掩盖未实现能力。
