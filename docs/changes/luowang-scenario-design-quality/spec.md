## 1. 范围与兼容边界

本变更补齐 Main 的变更证据、场景设计方法、初始化候选计划交接及质量验证。以下条款细化上游对“理解累计 diff”“形成初始化计划”和“有依据的场景”的要求；未涉及的产品、安全、发布和结果规则继续以上游为准。

保持现有六份 Built-in Role Instructions 资源及其确定性装载。普通 Run 仍创建四个隔离 Session；初始化直接验证仍创建六个，需人工审核的初始化仍在第三个 Session 后结束。两个 Main 阶段复用同一配置，不共享完整对话。

不新增数据库事实源、Run 工件类型、场景 frontmatter 字段、场景状态、结果状态、网站配置或发布 gate。本文中的决策表、能力表、执行清单只属于当前 `plan.md` 正文。历史 Run 和已发布场景不批量迁移。

## 3. 固定变更证据

### 3.1 Main 可用的只读能力

复用 Repository Service / GitRepository 获取事实，在 Main Planning 的受控工具中提供：

- 固定 `base_commit → target_commit` 的变更文件清单，记录新增、修改、删除、rename 的前后路径；无法判定 rename 时允许如实返回删除与新增。
- 按清单中的文件读取文本 diff，包含可定位的 hunk 和明确的 base/target。
- 按需读取固定 base 或 target 的文件内容，支持删除前的文件和 rename 前后内容；已有 target 读取能力继续有效。

上述能力仅对 Main Planning 开放，供日常规划和初始化中的证据核对使用。Runner 原有读取权限不扩大，Reviewer 和 Main Finalization 不获得通用仓库读取工具。工具不得接受任意 branch/ref/SHA、shell 片段或仓库目录；base/target 由 Harness 绑定到当前 Run。

### 3.2 空范围与受限结果

- `base_commit = null`：明确返回无比较基线，Main 按当前 target 理解基线，不把全部历史或所有文件伪装成本批 diff，也不擅自改变请求的 initialization 标记。
- base 与 target 相同，或最终内容无净变化：返回已成功计算的空变化；人工请求、强制包含标签和相关回归需求仍需独立判断，空 diff 不自动等于零场景。
- included commits 保持既有计算规则。Main 以固定前后净变化判断现存影响，不按提交数生成场景；场景/报告专属提交不变成新的产品测试需求。
- 清单与内容均有固定服务端输出上限和可续读分页：清单每页最多 100 项、文本每页最多 32 KiB。分页顺序稳定，游标绑定固定比较范围，调用方不能借游标指定其他 ref 或路径。
- 响应明确区分成功有内容、成功为空、分页未完、不可读和依赖失败；二进制、超限且无法续读的内容返回原因，不生成假文本。工具失败不得返回看似成功的空字符串。
- Main 必须续读与核心影响相关的未完整内容，或记录未读范围及其影响。没有完整证据时不能宣称已经审阅全部变化或证明无需场景测试。

### 3.3 路径和敏感信息

复用并覆盖到新增读取路径的现有相对路径、敏感文件与脱敏规则。rename 的两端都必须检查；删除文件的旧内容也受同一边界约束。拒绝目录穿越、绝对路径、symlink 解引用、submodule 内容和凭据文件读取。受限变化可返回不含敏感值的不可读标记，不能为了让 diff 完整而放开 Secret 边界。

当前 Run 的原始 diff、旧内容和受控工具错误不得自动全文复制到长期场景、报告或日志；仅引用必要的非敏感路径、规格章节和事实摘要。

### 3.4 场景检索上下文

场景索引摘要保留 ID、name、description、status、tags，并说明索引 commit 和同步情况。索引只用于检索；选择、修改、去重前必须核对 target 中的场景正文。索引陈旧或不可用时从 target 场景目录继续读取，不能把缓存为空视为仓库没有场景。

规划上下文提供现有生成语言和场景标签配置；配置约定必须包含的标签继续生效。新增字段只属于角色裁剪后的动态上下文，不增加网站配置或泄露测试账号。

## 4. 日常场景维护方法

Main 按“固定范围 → 理解契约 → 查看变化与相关调用关系 → 检索已有场景 → 决定维护动作 → 选择本次执行 → 记录缺口”工作。

先读项目理解和相关需求规格；intent、未确认计划、代码注释或历史 Bug 标题不单独构成已经确认的新业务期望。代码用于定位调用、状态和影响，实际运行用于记录观察；两者均不得单独反推正确期望。

| 变化类型               | 维护决策                                       | 本次测试                               |
| ---------------------- | ---------------------------------------------- | -------------------------------------- |
| 内部重构，契约未变     | 保留已有场景，不制造文案或 ID 变化             | 选择受影响的业务回归                   |
| 实现修复以满足既有契约 | 保留正确期望；仅在缺少回归覆盖时新增或补充场景 | 验证原问题及必要关联行为               |
| 已确认需求改变契约     | 修改对应场景，保持稳定 ID                      | 验证新的行为与必要拒绝路径             |
| 新独立能力或未覆盖风险 | 按业务语义去重后新增                           | 验证成功路径及适用的高风险边界         |
| 明确废弃能力           | 标记 deprecated，保留历史文件与 ID             | 检查必要的替代或拒绝行为               |
| 意图、规格与实现冲突   | 不放宽已有有效断言；新候选期望不明时保持 draft | 记录冲突与覆盖缺口，不能伪装为通过     |
| 纯非行为变化           | 保留资产；说明对产品行为无影响的证据           | 结合人工请求和配置决定是否无需场景测试 |

影响分析包括与变化有关的入口、调用方、共享权限、持久化、状态转换和外部依赖，不要求扫描所有无关文件。锁文件、配置、样式或文档变化不能仅凭扩展名认定无需测试。

每项实质性场景维护在计划中记录“变化证据 → 业务契约/风险 → 相关已有场景 → 决策及理由”。只解释相关候选和关键排除项，不为整个仓库生成维护台账。重用已有稳定 ID，不按 Run ID、时间戳或页面改名重新编号。

## 5. 场景写作契约

### 5.1 格式

沿用默认布局中的模板，文件平铺在 `docs/scenario-testing/scenarios/`，frontmatter 仅包含 `id`、`name`、`description`、`status`、`tags`。新增 ID 使用现有解析器允许的大写字母、数字和连字符。

内置指令提供一份完整的最小模板和少量正反例，正文包括目的、前置条件、步骤、期望、需要记录。字段名固定，name、description、正文和普通标签值遵循配置语言；`core` 等约定标签不翻译。

### 5.2 质量要求

- 一个场景围绕一个完整可判断的业务结果；跨页面或 API 的操作可组成同一场景。
- 前置写明角色、初始状态、必要依赖和合成数据条件；步骤可重复执行，不依赖未声明的前一场景残留。
- 期望是可观察、可判定的结果。避免仅写“正常”“正确”“成功”；明确必要的持久化、权限、拒绝后无副作用等断言。
- 每条关键断言说明需要记录的决定性证据；不把截图数量、日志数量或接口返回成功等同于业务完成。
- 数据创建、Run 标记、清理及删除后核验要求写清；长期场景使用语义描述，不嵌入本次 Run ID、临时地址、Secret 或真实账号。
- 使用业务可理解的操作定位；临时浏览器 ref、DOM 细节和本次命令输出留在执行工件中，不成为长期断言。
- 相同角色、前置、业务结果和风险的场景优先合并或复用；不同权限、关键断言、清理边界或独立失败原因不能为减少数量强行合并。
- `core` 只用于核心用户目标、严重数据/权限/资金后果或值得每次回归的行为，不给全部场景机械加标签。

### 5.3 期望依据与状态

按照上游证据优先级引用明确规格、已有可执行证据、运行观察和代码定位，并明确各自证明的内容。已有测试可以提供行为线索，但不能无条件压过已确认规格；资料冲突时写出冲突，而不是选择最容易让实现通过的期望。

`approved` 表示期望有明确依据；执行发现产品 Bug 不因此降为 draft。期望本身未确定才保持 draft。环境不可用时遵循上游初始化规则，只提交 draft 和阻塞说明，不声称建立已验证基线。

期望来源、冲突和状态理由写入当前计划及报告正文，不增加 frontmatter 字段。结构合法性由既有 parser/patch validator 保证；语义可执行性和证据充分性由明确指令、独立审核与质量评测验证，不宣称语法检查能证明语义正确。

## 6. 初始化方法与工件交接

### 6.1 静态勘察与运行时侦察

静态 Main 在现有 `plan.md` 中形成临时能力表：“角色/入口 → 核心目标 → 关键状态变化 → 风险 → 已知依据/待观察项”，并给 Runner 低风险侦察任务。缺少 `docs/PROJECT.md` 时在计划中形成临时理解，不代建项目理解文档。

侦察 Runner 记录已检查入口、角色状态、观察、未达路径、证据与清理情况；未观察到不等于功能不存在。它不伪造候选已通过，不声明正式场景进度。运行时观察是候选综合的输入，不自动变成正确期望。

### 6.2 候选综合和同一计划更新

候选 Main 必须先读取 plan、execution、draft-report，再核对必要的 target 事实，按业务语义生成或复用候选。它获得现有 `write_plan` 的受限能力，仅更新本次同一个 `plan.md`；保留静态依据及必要的侦察事实摘要，补充候选、期望依据、状态理由、执行安排、未覆盖风险及停止判断。

候选 patch 与更新计划必须一致；结束前两者均写入成功，或明确记录没有可信候选和原因。该阶段不能通过对话中的一段总结代替落盘交接。后续 Runner 与 Reviewer 读取更新后的计划，不能只依赖第一次静态计划。

策略允许时，Harness 应在候选 patch 应用后核对计划引用的工作场景，并按更新计划重新评估浏览器和必要验证前置。计划不一致或必要前置不可用时不得静默跳过场景后通过。

六个 Session 的职责不变；候选验证覆盖本次新增/实质修改且设为 approved 的场景。已有场景只按计划纳入，不因初始化标记自动全选。draft 的不确定期望记录为缺口，不纳入正式 passed/failed 判断；必要探索由初始化侦察承担。

### 6.3 停止与发布边界

初始化停止判断必须逐项说明：主要角色和入口已检查；每项核心能力具有成功路径候选或明确缺口；适用的权限、校验、持久化和外部依赖风险已覆盖或说明；所有 approved 候选有依据；策略允许时都已执行；最后复查入口/schema/现有测试未发现新的高价值核心能力。

达到时间或工具预算只能说明停止原因，不能证明覆盖完整。必要条件缺失时仍可结束本次尝试，但结果和初始化完成声明遵循 blocked 规则。结果聚合保持 `blocked > failed > passed`。

人工审核路径仍只保留 `scenario-changes.patch` 与 Harness 生成的 `report.md`；特殊报告应包含计划中必要的候选范围和覆盖缺口摘要，摘要经过既有脱敏且不改变报告 frontmatter。不能为保留计划而突破特殊工件 allowlist，不能等待 PR 合并或额外启动审核/验证 Session。Archiver 仍按原有模式发布 patch、关联 PR；最终 Main 修订未重新执行的候选仍 blocked。

## 7. 计划选择与独立审核

### 7.1 显式执行清单

扩充分析正文前，先消除“正文提到 ID 就选中”的歧义。新生成的正式验证计划使用唯一、固定标题 `## execution_scenarios`，其中以 Markdown 无序列表逐行只列稳定 ID，顺序即执行顺序；清单为空时写明“无需场景测试”及理由，不得混入 ID。固定标题是内部解析契约，其余说明遵循生成语言。

Harness、Runner 和进度工具共同使用该区域，其他区域的引用、排除理由、历史记录和 draft 候选不构成选中。拒绝重复标题、重复 ID、不存在 ID、deprecated/draft ID 和与已应用场景不一致的清单；沿用工件错误处理，不回退为全文 ID 搜索。初始侦察计划无需声明正式清单；候选 Main 负责补齐。

声明、开始、完成与最终场景结果必须对应清单，不能只执行任意子集却报告全部通过。缺失执行按现有阻塞/错误语义处理。旧 Run 只读展示保持兼容，不回写历史工件。

### 7.2 Reviewer 的可复核输入

计划为每个选中场景保留角色、前置、关键步骤、明确期望、依据定位和预期证据的必要摘要，使 Reviewer 在既有工具边界内可核对。新建/修改场景同时以本次 patch 核对，缺少必要摘要时不能自行补造。

Reviewer 先读固定计划与期望、存在的场景 patch 和原始证据，再对照 Runner 执行记录与草稿。统一角色指令与 Orchestrator 输出契约的顺序，避免“先读草稿”和“原始证据优先”同时出现。

审核增加场景设计检查：断言依据是否独立于实现、是否因失败放宽期望、是否漏掉已识别核心能力、是否重复或错误合并场景、执行是否符合清单。不能仅因 patch 路径和 YAML 合法就确认质量，也不能越权补测或读取其他 Session 对话。

## 8. 指令组织与质量评测

### 8.1 指令组织

共同证据规则写在 `common.md`；维护决策、写作契约和计划规则写在 `main-planning.md`；阶段交接、候选与停止标准写在 `scenario-initialization.md`。Runner、Reviewer、Finalization 仅补充各自需要的消费与审核规则。

保留“目标、硬边界、顺序、输出契约、失败规则、反模式”结构。固定方法只进入 system prompt 一次；run-id、提交、语言和配置属于动态上下文。Orchestrator 阶段契约与资源规则一致，不复制整套方法到 user message。沿用逻辑 ID、应用版本和 SHA-256 记录真实装载内容。

### 8.2 两类证明

工程验证用本地可控模型协议证明工具内容、边界、分页和交接，必须真实穿过生产 Session 路径。测试应让侦察阶段发现静态计划没有的新能力，随后生成不同候选并更新计划；不能预先把最终候选 ID 填进静态计划来掩盖交接缺口。

真实模型质量评测使用固定输入比较改进前后的生产规划路径。基线为本变更前的应用与指令版本；记录输入快照、diff、场景、侦察事实、应用 commit、指令 hash、模型/Thinking、配置、输出和失败原因。保持模型与输入一致，明确工具与提示词共同变化，不把总体提升单独归因于提示词文案。

至少覆盖以下八类：纯重构、已有契约的 Bug 修复、新能力、权限或持久化变化、明确废弃、需求/实现冲突、缺少项目理解文档的初始化、侦察新增能力或环境阻塞。每类预先列出预期维护决策、必须覆盖的业务风险和禁止编造的期望；允许不同但等价的场景拆分，不以固定文案或固定数量评分。

每个案例每个版本重复三次，保留全部输出，不能挑选最好的一次。由人工按同一标准复核，模型评分仅作辅助。比较无依据断言、遗漏必需风险、语义重复、不必要修改、不可执行场景及计划不一致的次数，并记录工具调用、耗时和可取得的 token 用量。

工程正确性与质量效果分开报告：权限/固定范围/交接等硬错误必须为零；质量项逐项报告基线与新版计数。声称“质量改善”需至少一项质量错误总数下降，其余不增加，并解释逐案例退步；若基线已无错误，只能报告维持质量。未达到条件则记录未证明改善，修订后重评，不以流程通过代替。

评测样例属于 LuoWang 开发测试夹具，不是罗网管理的正式场景资产。外部来源和完整非生产闭环固定为 `cynos-ai/cynos-website`，每次固定不可变 commit；不得切换测试目标或将 LuoWang 自身当作被测产品。纯设计对比不发布远端 patch/PR/Issue、不创建真实业务数据。真实调用需现有受控凭据及明确预算；缺少条件就记录未运行。脱敏结果放在既有 `.cynos/acceptance/` 输出区域，不在 change 目录增加评测报告、suite 或索引文件。
