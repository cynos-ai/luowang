# 场景维护与初始化质量改进 Intent

- 日期：2026-09-05
- 状态：需求基线；本轮只编写需求文档，尚未实施

## 当前问题

罗网已经具备独立角色、固定 target、场景 patch 校验、初始化侦察与验证、审核及归档流程，但流程能够完成并不等于模型能够稳定设计出有价值的场景。

日常测试要求 Main 理解累计代码变化，当前实际提供的主要是提交 SHA 和 target 文件现状，缺少可直接使用的前后变化证据。模型容易把“当前实现”误当成“本次变化”，遗漏删除、权限、默认值和上下游影响。

现有角色指令描述了职责和安全边界，但没有充分说明什么时候只需重跑，什么时候应该修改、新增或废弃场景。场景可能因内部重构被无谓改写，或者为迎合错误实现而放宽期望。

初始化要求生成少量高价值场景，但对核心能力、风险覆盖、可执行断言、语义去重和停止条件的指导过于概括。侦察后形成的候选依据和验证安排也不能完整更新给后续角色，容易让验证继续依赖过时的静态计划。

现有本地验收主要证明工具和 Session 流程。固定返回的候选场景不能证明真实模型的漏测、重复、无依据断言和不必要修改已经减少。

## 期望结果

- 日常场景维护能够依据真实、固定的变化事实，区分业务契约变化、实现修复和内部重构。
- 优先复用有效场景和稳定 ID；每次场景变更有明确业务理由，不因代码有变化就机械生成资产变化。
- 初始化能够为核心能力建立有依据、可执行的最小可信基线，并明确未覆盖风险和结束依据。
- 场景的前置、操作、期望、证据和数据清理要求足够具体，后续角色不需要猜测作者意图。
- 静态理解、运行观察、候选选择、实际执行和独立审核之间的交接完整、一致、可追溯。
- 能区分工程流程验证与真实模型质量证明，客观比较优化前后的结果，不承诺未经评测的提升。

## 影响

影响场景测试操作者、审核场景变更的人，以及 Main、Runner、Reviewer 对当前 Run 的理解和交接。工程影响集中在规划上下文、内置角色工作方法、场景计划交接和对应验证，不涉及控制台产品结构重做。

## 约束

- 遵循项目默认工件布局、MVP 场景规则和 v0.7 生产闭环边界。
- 保持 Main、Runner、Reviewer 三组配置、普通 Run 四个隔离 Session；初始化仍按现有顺序进行。
- 不使用 Pi Skills，不扩大为任意仓库读取或命令执行权限。
- 场景仍为 `draft | approved | deprecated`，Run 仍为 `passed | failed | blocked`；场景获准使用与产品是否通过是两件事。
- 维护模式、固定 target、Secret Store、数据清理、独立审核和 Archiver 写入边界保持有效。
- 外部测试目标仍是 `cynos-ai/cynos-website`；只使用非生产环境、合成数据和受控凭据。

## 非目标

- 生成穷尽所有页面、按钮、API 或代码分支的测试大全。
- 引入 suite、catalog、长期能力图、场景注册中心或另一套测试资产事实源。
- 自动修改产品代码、创建修复 Agent、增加角色配置、并行执行或新的审批状态机。
- 更换模型、升级依赖、改造控制台、发布新版本或操作真实外部测试环境。
- 把本次文档编写等同于实现完成或模型质量已经提升。
