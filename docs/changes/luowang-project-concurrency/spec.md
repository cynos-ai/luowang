# 项目独立并行测试 Spec

## 1. 范围与覆盖关系

本阶段包括 #118/#119 修复、#94 既有实现核验，以及项目间并行、项目内顺序执行和对应控制台展示。

实施后，本 Spec 覆盖 [多项目 Spec](../luowang-multi-project/spec.md) 中“全局同时最多一个 Run”、AC-MP-06 的全局单槽限制，以及 [UI Spec](../luowang-v07-ui-redesign/spec.md) 中单个当前执行和全局顺序位置的展示要求。旧版本验收事实保持不变；本文件在开发前描述目标行为，不宣称当前系统已支持。

未修改的项目归属、固定 target、prepared/resolved、场景审批、归档和恢复规则继续生效。[单向交接](../luowang-single-handoff/spec.md)、[模型语义判断](../luowang-model-semantic-decisions/spec.md)、[证据读取](../luowang-retest-followup/spec.md) 和 [截图采集完整性](../luowang-screenshot-capture-integrity/spec.md) 的最新边界不变。正常 Run 仍为四个隔离 Session，不启用 Pi Skills。

## 2. 并发与配置

### 2.1 执行规则

- 每项目最多一个处于准备、模型执行或 Harness 收尾中的请求；同项目 queued 按 queueId 顺序处理。
- 不同项目可同时占用执行名额。一个项目正在准备目标、构建镜像或等待模型，不得阻止其他项目使用空闲名额。
- 部署并发上限指上述已认领请求数，而不是当前模型 HTTP 请求数、浏览器数量或累计排队数。目标尚未解析、Run 尚未创建时也计入占用。
- 从原子认领开始占用，到 Run 完成且执行资源释放、进入 waiting_archive，或准备/执行失败完成必要收尾后释放。正在进行的 Harness 清理不能提前释放项目执行约束。
- waiting_archive 不占全局执行名额，但按旧规则阻止本项目下一请求；其他项目可以继续。归档完成后按既有完成/重试/推进规则处理，不因并行另设无限等待门禁，也不把归档失败改成测试失败。
- 空闲名额按现有项目轮转顺序填满；竞争下不超额、不重复认领、不允许同项目第二个请求抢占。上限为 1 时保留当前跨项目轮转语义。

### 2.2 部署设置

首版通过启动配置 `LUOWANG_MAX_CONCURRENT_PROJECTS` 设置并发上限，默认 2；接受 1–8 的十进制整数，缺省用默认值，空值、非整数和越界值启动失败，不静默回退。8 是配置校验上限，不是已证明的容量承诺。

配置由 Compose/启动环境传入，系统状态及工作台只读显示实际生效上限；本阶段不增加热修改入口。设为 1 可恢复串行调度，但不能据此声称已经回滚程序或数据库。升级部署前需明确默认值变化，完成停机与备份安排；保守部署可显式设为 1，验证后改为 2 并重启。

不按项目数量自动扩大并发，不增加项目优先级或为每个项目启动一套罗网服务。更高并发需要操作者依据 CPU、内存、浏览器和模型限额选择，首次真实容量证明固定为 2。

## 3. 调度与生命周期

- 继续使用现有 SQLite 队列和 Coordinator/Dispatcher，不增加消息队列、分布式租约或新 Run 结果状态。
- 认领事务同时验证全局剩余名额、项目 active、项目不存在 running/waiting_archive 和队首归属。所有生产认领入口共用该规则，不保留能绕过容量检查的旁路。
- 暂停与认领竞争有确定结果：先暂停则不认领；先认领则任务按固定上下文继续。暂停不隐含取消，待归档和历史读取仍允许。
- Dispatcher 按 projectId/queueId/Run ID 跟踪所有活动任务。并发完成、失败和 finally 只释放本任务登记；A 完成不能清除 B 的活动状态或容器。
- 手工请求、自动轮询、定时触发、完成回调同时唤醒调度时，不重复执行。任务占满名额时不忙轮询；名额释放或新请求到达应再次检查队列，避免唤醒丢失。
- 后台 tick 不得因等待整批模型 Run 完成而长期停止轮询、索引和归档重试。复用既有调度器，区分触发调度与等待全部任务结束；服务退出时停止新认领并等待/记录全部已跟踪任务，不能只等待一个 Run。
- 单项目失败分别记录且释放名额。公共 Provider、OSS、Docker 或数据库故障如实报告公共影响，不承诺共享依赖故障下其他项目仍可成功；不新增 Git/模型自动重试策略。

## 4. 并行隔离与共享资源

- 服务从已认领请求装配固定项目上下文，保持 repository、工作目录、Secret scope、测试环境和清理地址绑定。固定 target 和镜像 digest 不随其他项目、页面切换或配置变化改变。
- 每个 Run 使用独立 Session、MCP 子进程/浏览器状态、下载和证据目录、命令容器、HTTP Cookie 客户端与临时数据登记。角色方法可共享，只读方法资源不能变为共享可变会话。
- 敏感值登记与脱敏、证据列表与读取、OSS 路径和清理回执按本 Run 隔离；相同场景 ID、文件名和相对路径不产生覆盖。错误释放与跨项目读取必须拒绝。
- 同项目 Git clone 上的准备、索引、归档和后台操作保持既有受控互斥；审计既有锁的归属与所有调用路径，不能以跨项目全局大锁代替项目内一致性。已发布报告与场景 patch 的幂等边界不变。
- 模型/浏览器共享配置和 Provider 凭据在任一项目准备或执行期间仍禁止变更。项目任务语义配置、测试与清理凭据仍只受本项目活动请求约束；Git/OSS 凭据轮换沿用固定目的地规则。
- Docker 资源只能按实例、项目、Run 所有权操作。正常完成只释放本 Run；启动孤儿回收只能在新任务认领前进行，不能在另一个 Run 活跃时重新执行实例级清理。
- 两个项目共用目标应用账号、数据库或清理域时，Harness 的目录隔离不能证明业务数据隔离。本轮 live 使用各自独立的非生产应用/数据域和合成账号；首版不实现外部环境冲突自动识别或共享环境锁。

## 5. 重启、恢复与历史保留

- 启动先核对本实例资源及全部 in-flight 请求，完成恢复协调后再放行新认领；恢复过程可恢复待归档工作，但不能与新执行交叉误删资源。
- 已存在 prepared/resolved 的未启动请求按现有 internal ref 和远端历史核对恢复，不重建 prepared commit，不重新解析移动 HEAD。
- 已启动但未完成的每个模型 Run 按现有 interrupted 规则保留，不自动续跑 Session、不自动重跑模型、不伪造清理成功。若完成事实存在但队列更新中断，复核后只恢复归档。
- 重启时 A/B 同时在不同阶段也必须逐项处理；同一请求仍只关联原唯一 Run。任一项目的恢复异常不得让其他项目记录被覆盖；无法确认的公共所有权错误仍需停止相关启动流程。
- 升级保留历史 Run、报告、证据、结果与项目归属。若实现需要 schema 变更，提供事务迁移和隔离副本回退证明；不把“无需新增数据库”提前当作已确认实现事实。
- 失败、清理告警与归档状态继续独立。重启不能把 interrupted 或未完整验证的任务变为 passed，收尾失败不能推翻已经成立的测试结论。

## 6. API 与控制台

- 工作台由单个 activeRun 改为活动任务集合，包含准备中尚无 Run ID 的请求。项目、queueId、Run ID（允许尚无）、阶段、固定提交（允许尚未解析）、开始/更新时间及现有进度均来自真实数据。
- 服务端提供实际占用数和生效上限；展示“2/2 个项目正在处理”等事实。准备阶段无场景进度时不伪造百分比。
- 各项目页只读取其当前活动任务；A 完成或切换项目不能使 B 消失。更新 dispatcher、共享类型、路由、读模型和消费页面，不保留返回任意一个 Run 的虚假兼容字段。
- 队列显示本项目顺序与具体等待原因：本项目任务执行中、本项目待归档、项目暂停、全局名额已满或尚待调度。并发下不把全局数据库序号显示为严格的实际开跑名次，不估算未经测量的开始时间。
- 部分项目读取失败时，其余任务继续可见；缓存标记陈旧，认证、项目归属、AbortController/资源键和迟到响应保护不变。
- 同步修改工作台、项目列表/概览、测试页、系统状态及受影响导航，维持 768px 最低视口和既有可访问性要求，不新增独立监控中心。

## 7. 本阶段缺陷收敛

- #118：模型目录的加载/成功/空/失败状态以紧凑区域展示，不占据角色卡片单元。核对 1440px、768px 下角色排列及新旧 CSS 作用范围。
- #119：在有垂直滚动条时，工作台、系统状态、模型设置及代表性项目页整页 `scrollWidth <= clientWidth`，允许明确局部表格滚动，不能用裁切或隐藏内容冒充修复。现有 E2E 已使用 clientWidth，必须补实际漏测条件，不只重复同一断言。
- #94：复用已有 Git 操作 timeout/子进程终止/askpass 清理；验证 stalled remote 经生产 readiness API 到页面仍明确显示超时、项目未就绪、无 target/image 伪造及凭据泄露。必要时修正错误传递，不扩为代理配置或自动重试项目。
