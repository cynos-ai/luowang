# 同一操作者管理多个 Git 项目 Intent

- 状态：v0.6.0 需求草案。负责人提出支持同一个用户的多个 Git 项目；下述产品边界为建议，尚未形成实现规格。
- 日期：2026-09-23
- 基线：v0.5.0；关联 [代码深读](../luowang-code-understanding/intent.md)。

## 问题

当前部署只保存一份目标仓库配置，场景 ID 在索引中全局唯一，Run 没有独立项目归属字段，调度器也采用全局状态键。操作者无法在一次登录后分别管理多个仓库的测试任务、凭据和历史。

多项目支持需要让仓库、环境、凭据、场景和后台任务有明确归属，仅在页面中增加仓库切换不能解决这些问题。

## 期望结果

1. 同一操作者可以创建、查看和切换多个项目，分别触发测试及查看场景、历史、队列、同步状态和归档结果。
2. 不同项目允许存在相同的场景 ID 和仓库相对路径，其内容与结果互不覆盖。
3. 凭据、测试环境、清理操作、源码读取、模型上下文和证据访问都对应当前任务所属项目；不得读取或使用其他项目的数据。
4. 任务创建后归属固定。页面切换、配置更新、重启恢复和归档重试都不能让已有任务改投另一个仓库或环境。
5. 每个项目独立记录固定测试提交、推进位置及同步状态。一个项目的失败可见且可恢复，不应阻止其他项目后续获得执行机会。
6. 项目暂停后停止接受或调度相应的新测试，历史仍可查；运行中任务、待归档任务和恢复行为需有明确规则。

## 产品范围建议

- 保留现有单操作者登录方式；每个项目对应一个 GitHub 仓库、一条场景测试分支和一个非生产测试环境。
- 第一阶段全局一次执行一个 Run，项目内保持顺序；项目间调度应防止某个项目持续占满队列而使其他项目长期无法运行。
- 模型和 OSS 可使用部署级配置，项目数据、证据路径和任务上下文仍明确隔离；具体配置共享与覆盖规则在 spec 确定。
- 先支持项目创建、查看、切换、暂停及恢复；永久删除项目及历史清除另行确定。

## 影响与约束

- 涉及配置与 Secret Store、SQLite、仓库工作目录、API、控制台、Run、队列、索引、归档、证据及重启恢复。
- 深读方法可以共用，但理解结论和源码事实必须归属于具体项目及提交。
- Git 继续保存各目标项目的长期场景和正式报告；数据库保存运行状态、Secrets 与可重建缓存，不建立跨项目混合资产库。
- 保留场景 patch 权限、不可变 target_commit、独立审核、真实清理和自动归档规则。
- 延续负责人此前“不考虑兼容性”的要求，不为旧接口或旧配置格式保留并行兼容层；这不授权删除既有数据库或历史 Run。升级时旧数据如何保留或导入需在规格中说明。
- 现行默认布局、PROJECT.md 和 MVP 规格中的单仓库边界需由新 spec 明确覆盖，不能把本草案当作已经实现的能力。

## 非目标建议

- 多用户注册、组织、团队权限或多租户平台。
- 单个项目关联多个仓库、一个仓库的多环境测试矩阵。
- 本版本引入跨项目并行 Run 或分布式执行集群。
- 自动部署目标项目或为测试补充未获授权的外部资源。

## 验收方向建议

至少两个获授权的非生产目标，使用相同场景 ID 和相对报告路径验证隔离；交替触发任务，并覆盖运行中切换项目、配置修改、失败重试、重启恢复、暂停与恢复。分别核对实际使用的仓库、凭据、环境、清理对象、证据和归档目的地。一个项目的依赖失败后，另一个项目仍应可以执行。真实模型调用预算和新增测试目标在执行前明确。

## 待在规格阶段确定

- 项目级与部署级配置的划分，配置修改对已排队和运行中任务的影响。
- 调度顺序、暂停行为及归档失败后的处理方式。
- 已有单仓库数据的归属及升级操作，不覆盖旧测试事实。
- 同一仓库重复接入的处理；建议第一版拒绝重复接入同一个 GitHub 仓库。
- 两项目联合验收的具体目标与预置测试条件。
